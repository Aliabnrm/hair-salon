# ADR-002 — سازمان‌دهی کد و مرز مسئولیت‌ها
تاریخ: ۲۰۲۶-۱۰-۲۹؛ وضعیت: قرارداد مهندسی جاری بر اساس درخواست کارفرما. محدوده اجرا همچنان تابع اسپرینت مصوب است. این سند ساختار مورد انتظار را تعیین می‌کند، نه ادعای وجود کد.

## زمینه و تصمیم
تیم یک کارفرما و دستیار است؛ محصول رزرو برای ایران و بک‌اند NestJS است. هدف، ساخت قابل نگهداری همراه با یادگیری است. سازمان‌دهی بر اساس قابلیت (feature-first) و معماری Modular Monolith انتخاب می‌شود. لایه‌های domain/application/infrastructure/presentation برای قابلیت‌های پیچیده به‌تدریج ایجاد می‌شوند؛ Health ساده Controller و Service دارد.

قانون پایه: HTTP/نمایش، اجرای سناریو، قوانین کسب‌وکار و I/O مسئولیت مستقل دارند. domain پیچیده، TypeScript خالص و مستقل از Nest/React/ORM است. Application Service می‌تواند Injectable باشد و orchestration کند، اما قانون زمان‌بندی متعلق به دامنه است. ارتباط با DB یا SMS از یک مرز مشخص عبور می‌کند. وابستگی از بیرون به سمت قواعد است؛ قواعد دامنه، Controller یا ORM را import نمی‌کنند.

فرانت نیز feature-first است؛ صفحه route ترکیب‌کننده، component مسئول نمایش/تعامل محلی، hook مسئول منطق stateful مرتبط و api مسئول I/O است. منطق خالص در تابع عادی قرار می‌گیرد، نه hook بی‌نیاز از React. قیمت نهایی، مجوز و صحت رزرو همواره در سرور اعمال می‌شوند.

## ساختار و مرجع جزئیات
[ساختار فایل‌ها](../codebase-structure.md) مرجع پوشه و جهت import است؛ [استاندارد بک‌اند](../../engineering/backend-standards.md) و [فرانت](../../engineering/frontend-standards.md) رفتار لایه‌ها را تعریف می‌کنند. [کیفیت](../../engineering/quality-gates.md) مرجع بررسی است. این اسناد را به جای تکثیر در هر اسپرینت ارجاع دهید.

## گزینه‌های کنار گذاشته‌شده و پیامد
ساختار سراسری controllers/services/repositories مرز قابلیت را کمرنگ می‌کند؛ برای این پروژه انتخاب نشد. چهار لایه اجباری برای تک‌تک endpointها، interface برای هر کلاس، GenericRepository و BaseService عمومی هزینه یادگیری/تغییر بدون نیاز ایجاد می‌کنند. microservices و CQRS نیاز عملی اثبات‌شده ندارند.

پیامد مثبت: پیدا کردن کد یک قابلیت آسان، تست قوانین مستقل و تغییر adapter قابل کنترل است. هزینه: رعایت مرز import نیازمند review است؛ ماژول‌بندی به‌تنهایی مانع coupling نمی‌شود. کاهش ریسک: public export محدود، پرهیز از چرخه و import داخلی ماژول دیگر، و افزودن بررسی خودکار مرزها وقتی چند ماژول واقعی شکل گرفتند.

DRY بر اساس مسئولیت و دلیل تغییر سنجیده شود: قانون یکسان رزرو میان مسیر آنلاین/دستی مشترک است؛ شباهت اتفاقی دو UI دلیل ساخت component همه‌کاره نیست. استخراج مشترک بعد از روشن‌شدن الگو انجام شود. SOLID با مسئولیت روشن و وابستگی قابل جایگزینی اعمال شود، نه با زیادکردن فایل‌ها.

مبنای بیرونی و محدودیت شواهد در [منابع](../../references/engineering-sources.md) ثبت شده؛ این ساختار رتبه‌بندی یا کپی یک «بهترین مخزن GitHub» نیست. تغییر مرز اصلی یا اضافه‌کردن سرویس مستقل نیازمند ADR جایگزین و بررسی اثر بر اسپرینت است.
