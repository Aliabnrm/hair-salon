# ADR-011 — زمان‌های پیشنهادی بر اساس برنامه و ساعت تهران

تاریخ: ۲۰۲۶-۱۱-۰۳؛ وضعیت: تصمیم اجرایی اسپرینت۶. مرجع محدوده: [طرح۶](../../planning/sprints/sprint-06-plan.md).

## تصمیم و دلیل

Availability در bounded context موجود `salon-management` و خواندنی است. برنامه سالن و متخصص، exception، خدمت و بافر از یک SELECT و snapshot همان statement خوانده می‌شوند. snapshot دوم، query شبکه برای هر متخصص و کپی جدول عمومی نداریم. وضعیت published، دسته فعال، خدمت فعال و متخصص فعال/عمومی/تخصیص‌یافته در همین خواندن شرط‌اند. ویرایش مدیریت همچنان سالن را طبق ADR-009 از انتشار خارج می‌کند؛ درخواست بعد از commit وضعیت جدید را می‌بیند. درخواست هم‌زمان می‌تواند snapshot قدیمی منسجم را ببیند.

Domain خالص، ورودی برنامه و `now` صریح می‌گیرد؛ Clock مرز واقعی زمان سرور برای Application و تست است. ساعت کاربر مرجع اعتبار نیست. Reader مسئول PostgreSQL و Controller مسئول HTTP/سهمیه/پاسخ امن است. سرویس هماهنگ‌کننده قانون slot را تکرار نمی‌کند.

خط مبنا دفتر اشغال یا Appointment ندارد. پاسخ صریحاً `availability_basis=schedule_only` و `booking_enabled=false` است؛ mapping سرویس، busy ورودی موتور را خالی می‌گذارد و دلیل را در کد بیان می‌کند. این انتخاب نتیجه شکست I/O نیست؛ شکست خواندن پاسخ503 دارد. بازه اشغال در موتور خالص پشتیبانی و فقط در تست وارد می‌شود. هیچ جدول فرضی، رزرو، hold، fake repository یا وعده ظرفیت ساخته نشده است. اتصال دفتر اشغال و ثبت اتمیک، تصمیم اسپرینت بعد است.

## معنا و تبدیل زمان

- بازه‌ها نیمه‌باز `[start,end)` و اشغال برابر `[start-bufferBefore,end+bufferAfter)` است. بافر busy قبلی دوباره اعمال نمی‌شود.
- exception هر scope جای برنامه هفتگی همان scope را می‌گیرد. برنامه‌های مؤثر ابتدا مستقل، سپس intersect می‌شوند. تعطیلی سالن مقدم است؛ نبود برنامه بسته است. فقط مجاورت واقعی ادغام می‌شود.
- گام شروع۱۵دقیقه بر نیمه‌شب محلی تراز می‌شود؛ حداقل فاصله۶۰دقیقه، با مرز دقیق مجاز؛ افق۳۰روز محلی از امروز تهران تا today+29؛ query حداکثرهفت روز inclusive.
- آغاز24:00 تولید نمی‌شود؛ پایان دقیق مرزروز مجاز است. مدت، زمان سپری‌شده واقعی است و خدمت/اشغال از روز محلی بیرون نمی‌روند.
- `@js-temporal/polyfill@0.5.1` فقط در backend نصب شد: `Temporal` در Node24.22.2 این محیط موجود نبود. بسته با Node نصب‌شده و TS6 بررسی شد؛ دو ورودی lockfile اضافه شد، ارتقای کلی انجام نشد. APIهای IANA/PlainDate/Instant و transition، جای الگوریتم دستی DST را می‌گیرند.
- ساعت ناموجود با round-trip تشخیص داده و حذف می‌شود؛ ساعت تکراری دو instant مستقل دارد. روز در transitionهای واقعی IANA به segmentهای offset ثابت شکسته می‌شود تا یک شیفت کوتاه در ساعت تکراری، فاصله بیرون از شیفت را اشتباه مجاز نکند. بازه‌های پیوسته روی محور instant دوباره ادغام می‌شوند.

## قرارداد و UI

GET عمومی no-store با query allowlist، پاسخ محدود و شمارش متخصص عمومی؛ حالت any اجتماع زمان‌ها را با کلید شروع/پایان UTC جمع می‌کند. تعیین متخصص نهایی صورت نمی‌گیرد. سقف دفاعی۷۰۰slot خطای503 می‌دهد؛ حذف خاموش نداریم. سهمیه فعلی catalog برابر۱۸۰ و سهمیه اختصاصی محاسبه۶۰درخواست/IP/دقیقه است؛ شمارنده همان سازوکار امنیت موجود را مصرف می‌کند.

URL محل service/staff/date است. ساعت انتخابی فقط state رابط است؛ پس از دریافت تازه فقط در صورت حضور در slotهای همان intent نمایش داده می‌شود. پاسخ قبلی هنگام refresh/خطا قابل انتخاب نیست. `useRemote` درخواست قبلی را abort و پاسخ دیررس را با sequence/key کنار می‌گذارد. API اولیه بدون تاریخ، policy سرور را bootstrap می‌کند؛ تاریخ منقضی با اقدام اصلاح روشن پاسخ می‌گیرد. تقویم از تاریخ محلی ISO، نمایش شمسی و هفته شنبه استفاده می‌کند. ورود اجباری نیست.

## گزینه‌ها و پیامد

محاسبه در SQL یا UI رد شد: تکرار قوانین و دشواری تست ایجاد می‌کند. ساخت ماژول رزرو کامل/CQRS/Redis نیاز فعلی ندارد. offset ثابت تهران تاریخچه را غلط می‌کند؛ Date/Intl به‌تنهایی تبدیل معکوس و gap/fold مطمئن را ساده نمی‌کنند. کتابخانه تاریخ تازه در frontend لازم نبود؛ Intl و helper موجود کافی‌اند.

این برش migration ندارد. EXPLAIN واقعی و سنجش کوچک در [گزارش۶](../../planning/sprints/sprint-06-report.md) ثبت می‌شوند؛ داده۵۰متخصص benchmark بار واقعی نیست. no-store درخواست تازه را تضمین می‌کند؛ push فوری تغییر برنامه و تضمین رزرو از آن برداشت نمی‌شود. محدودیت NAT و proxy همچنان طبق سند امنیت پابرجاست.
