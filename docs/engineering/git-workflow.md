# روند Git، بازبینی و تاریخچه پروژه

تاریخ: ۲۰۲۶-۱۰-۲۹. مرجع remote: [Aliabnrm/hair-salon](https://github.com/Aliabnrm/hair-salon). کارفرما ایجاد Git محلی، commit/push و استفاده از Pull Request را برای این پروژه درخواست کرده است. این اجازه شامل انتشار سرویس، تغییر visibility یا بازنویسی تاریخچه remote نیست.

## از نیاز تا تغییر قابل بررسی

1. نیاز و محدوده در طرح اسپرینت با شناسه پذیرش ثبت و تأیید شود؛ تصمیم مهم فنی در ADR دلیل و گزینه جایگزین داشته باشد.
2. پرامپت اجرایی از همان طرح نوشته شود؛ سپس branch مربوط از مبنای درست ساخته شود. main محل نسخه‌های مرورشده است.
3. تغییر در گام‌های معنادار انجام شود؛ هر commit یک هدف روشن داشته باشد. commitهای قبلی پروژه حفظ شوند؛ تاریخ، نویسنده یا فعالیت گذشته جعل نشود.
4. بررسی‌های متناسب، بازبینی diff و بررسی فایل‌های حساس انجام شود. source، migration و مستند لازم commit شوند؛ env خصوصی، node_modules، dist، work، کلید و token وارد Git نشوند.
5. branch روی origin push و PR با مشکل، نتیجه، دلیل، تست واقعی و محدودیت ساخته شود. CI باید برای همان commit نهایی موفق باشد.
6. PR آمادهٔ مرور کارفرما تحویل شود؛ merge خودکار در روش فعلی نداریم. پس از merge، branch محلی با main هماهنگ و کار بعدی از مبنای درست آغاز شود. PR تأییدنشده با push مستقیم main دور زده نشود.

در تیم دو نفره، بازبینی دستیار و بررسی خودکار کمک‌کننده‌اند؛ بازبینی مستقل انسانیِ انجام‌نشده را ادعا نمی‌کنیم. شاخه اسپرینت ۲ تا مرور پایه اسپرینت ۱، از baseline مشخص مشتق می‌شود؛ برای داشتن تاریخچه ساده ترجیح این است که ابتدا PR پایه ادغام شود، سپس PR اجرای اسپرینت ۲ ساخته شود.

## نام‌گذاری و اندازه تغییر

- شاخه‌ها: `chore/sprint-01-foundation`، `docs/sprint-02-plan`، `feat/sprint-02-database` یا `fix/<specific-problem>`؛ نام، موضوع واقعی تغییر را بیان کند.
- پیام commit انگلیسی و روشن، مانند `feat(health): add database readiness probe` یا `docs: define database migration policy`. انواع رایج: feat، fix، docs، test، ci، refactor و chore. scope وقتی مفید است اضافه شود.
- یک commit برای یک هدف منسجم؛ تغییر رفتار، اصلاح تست همان رفتار و توضیح ضروری آن می‌توانند همراه باشند. تفکیک نمایشی یک تغییر یا commit بی‌معنای «update» ارزش تاریخچه را کم می‌کند.
- تاریخچه اسپرینت ۱ اکنون ثبت می‌شود؛ چند روز فعالیت ساختگی یا commit با زمان گذشته ایجاد نمی‌شود.

برای PR دارای commitهای معنادار و مرتب، گزینه معمول ما merge commit است تا هم PR و هم commitها حفظ شوند. اگر commitها شامل اصلاحات موقت حین کار باشند، squash با یک پیام دقیق مناسب‌تر است. روش نهایی هنگام مرور PR انتخاب شود؛ force-push به main ممنوع و بازنویسی branch منتشرشده بدون هماهنگی انجام نشود.

## بررسی خودکار

Workflow `.github/workflows/ci.yml` روی PR و push به main اجرا می‌شود: Node از `.nvmrc`، بررسی npm مطابق packageManager، نصب از lockfile و `npm run check`. check فعلی build، typecheck، lint، format و ۴۶ تست پایه را اجرا می‌کند؛ تعداد تست ثابت نیست و با قابلیت واقعی رشد می‌کند.

GitHub Actions رسمی با SHA دقیق بررسی‌شده pin شده‌اند؛ checkout v7.0.1 و setup-node v7.1.0 هر دو runtime node24 دارند. workflow فقط `contents: read` دارد و credential در checkout نگه نمی‌دارد. dependencyهای اجرایی هم در lockfile ثبت شده‌اند. موفقیت محلی و موفقیت GitHub دو شاهد جدا هستند؛ تا اجرای واقعی CI، موفقیت remote ادعا نشود.

تست دیتابیس و سرویس PostgreSQL در اسپرینت ۲ به همین workflow اضافه می‌شوند؛ اکنون workflow وانمود نمی‌کند DB را آزمایش کرده است. نصب و build از clone تمیز بررسی شود و به work/runtime شخصی تکیه نکند.

پیشنهاد تنظیم محافظت main پس از اولین CI موفق: اجبار PR و check با نام `API quality`، حل گفتگوها و منع force-push. برای تیم فعلی، الزام بازبین انسانی دوم یا signed commit بدون زیرساخت مرتبط تحمیل نمی‌شود. این فایل به‌تنهایی branch protection را فعال نمی‌کند؛ وضعیت اعمال واقعی باید گزارش شود.

## معنای رزومه‌ای این روند

PR باید نشان دهد چه مسئله‌ای وجود داشت، چرا راهکار انتخاب شد و صحتش چگونه بررسی شد. شواهد ارزشمند پروژه، کد خوانا، ADR مستدل، تست رفتار، CI واقعی، migration قابل مرور و محدودیت صادقانه است؛ تعداد commit یا badge جای آن‌ها را نمی‌گیرد. مجوز متن‌باز، معرفی عمومی و اطلاعات تماس بدون انتخاب کارفرما اضافه نمی‌شوند.
