# روند Git، بازبینی و تاریخچه پروژه

تاریخ به‌روزرسانی: ۲۰۲۶-۱۰-۲۹. مرجع remote: [Aliabnrm/hair-salon](https://github.com/Aliabnrm/hair-salon). این نسخه طبق دستور جدید کارفرما، **جایگزین مجوز قبلی commit/push خودکار دستیار** است؛ متن پرامپت‌های تاریخی اسپرینت‌های ۱ و ۲ این محدودیت تازه را لغو نمی‌کند.

## نقش شاخه‌ها

- `main`: نسخه ادغام‌شده و مرورشده پروژه. ورود تغییر از PR و پس از موفقیت CI است.
- `dev`: مبنای جاری توسعه؛ قبل از شروع هر کار با `origin/dev` هماهنگ می‌شود. PR قابلیت‌ها و اصلاح‌ها به این شاخه می‌روند.
- `feat/<topic>`: قابلیت تازه؛ `fix/<topic>`: رفع باگ؛ `refactor/<topic>`: تغییر ساختار بدون تغییر رفتار. تغییر مستندات نیز شاخه جدا مانند `docs/dev-workflow` دارد.

مسیر معمول: `dev → شاخه کار → PR به dev → PR از dev به main`. ساخت شاخه یا اجرای اسپرینت بعدی به‌خودی‌خود اجازه شروع دامنه تأییدنشده نیست. default branch مخزن همچنان main است؛ base هر PR توسعه باید صریح dev انتخاب شود.

## از نیاز تا تحویل محلی

1. نیاز و محدوده در طرح اسپرینت تأیید شود؛ تصمیم مهم فنی در ADR ثبت شود. پیش از تغییر، وضعیت Git و فایل‌های موجود بررسی و تغییر کارفرما حفظ شود.
2. `git fetch origin`، رفتن به dev و `git pull --ff-only origin dev`؛ سپس شاخه اختصاصی از dev به‌روز ساخته شود. اگر تغییر محلی یا تاریخچه واگرا مانع شد، با reset/clean/stash خودکار داده کارفرما جابه‌جا یا حذف نشود؛ علت بررسی شود.
3. پیاده‌سازی، تست واقعی متناسب و مستندات/درس لازم روی همان شاخه انجام شوند. دستیار تغییرهای جدید را commit، push یا منتشر نمی‌کند؛ main و dev محل پیاده‌سازی مستقیم نیستند.
4. diff، مرز importها، cleanup، خطا و داده حساس بازبینی شوند. در پایان، شرح تغییر، نتیجه واقعی تست‌ها، محدودیت‌ها و **متن پیشنهادی commit انگلیسی** ارائه شود. متن PR هم می‌تواند برای مرور آماده شود. تغییرهای محلی برای بررسی کارفرما باقی بمانند.
5. **کارفرما بررسی و سپس commit/push می‌کند.** source، migration و مستند لازم ثبت شوند؛ env خصوصی، node_modules، dist، work، کلید و token وارد Git نشوند.
6. پس از push کارفرما، با دستور مربوط PR از شاخه کار به dev ساخته/بررسی شود. نتیجه CI همان SHA بررسی شود؛ موفقیت محلی جای CI remote نیست. در تیم دو نفره، مرور دستیار جای بازبینی مستقل انسانی معرفی نشود.
7. merge PR تنها با دستور صریح کارفرما انجام شود. انتقال dev به main نیز PR جدا و بررسی CI خودش را دارد؛ ادغام خودکار، push مستقیم main/dev یا شروع خودکار اسپرینت بعد نداریم.

نمونه شروع کار با فرض تمیزبودن درخت کار و نبود شاخه هم‌نام:

```sh
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c feat/example-topic
```

پس از پیاده‌سازی، دستیار پیام commit را پیشنهاد می‌دهد؛ اجرای commit/push با کارفرماست. اگر شاخه کار از قبل وجود دارد، به جای ساخت دوباره همان شاخه بررسی و ادامه داده شود.

## مرز مجوز و تاریخچه

درخواست صریح merge یا ساخت شاخه remote، فقط همان عملیات را مجاز می‌کند؛ مجوز ثبت و push پیاده‌سازی تازه از آن برداشت نشود. در گذار فعلی، کارفرما ادغام اسپرینت‌های ۱ و ۲ در main و ساخت اولیه dev را صریحاً خواست. اصلاح همین روند به‌صورت محلی در شاخه مستندات تحویل می‌شود و دستیار آن را commit/push نمی‌کند.

برای PR با commitهای معنادار، merge commit انتخاب معمول است تا تاریخچه حفظ شود؛ squash تنها هنگام مرور و با تصمیم مربوط. force-push، بازنویسی شاخه منتشرشده یا جعل زمان/نویسنده انجام نشود. رفع تعارض باید تغییرهای هر دو طرف را حفظ کند؛ ثبت و push نتیجه جدید نیز طبق قاعده دستی بالاست.

پیام commit انگلیسی و روشن، مانند `feat(auth): add mobile sign-in`، `fix(health): release timed-out connections` یا `docs: adopt dev workflow and manual commit policy`. هر commit یک هدف منسجم داشته باشد؛ تعداد commit یا badge جای دلیل و شاهد تست را نمی‌گیرد.

## بررسی خودکار و محافظت شاخه‌ها

Workflow `.github/workflows/ci.yml` روی همه PRها، از جمله PR به dev، و push به main اجرا می‌شود: Node از `.nvmrc`، بررسی pnpm مطابق packageManager، نصب frozen از pnpm-lock.yaml و `pnpm run check`. check شامل build/typecheck/lint/format:check و unit/HTTP/integration واقعی PostgreSQL است. CI از PostgreSQL 17.11 با image/digest هماهنگ Compose و env فقط تست استفاده می‌کند.

GitHub Actions رسمی با SHA دقیق pin شده‌اند؛ workflow فقط `contents: read` دارد و credential در checkout نگه نمی‌دارد. نصب و build از checkout تمیز باید مستقل از work/runtime شخصی باشد. پس از push جدید کارفرما، CI همان commit تازه دوباره بررسی می‌شود.

main و dev از مسیر PR و check با نام `API quality`، به‌روز بودن با base، حل گفتگوها و منع force-push/حذف شاخه محافظت می‌شوند؛ شامل admin هم می‌شود. approval اجباری صفر است تا تأیید خود به‌جای بازبینی مستقل جا زده نشود. وضعیت واقعی باید از GitHub بررسی شود؛ وجود این متن جای enforce سرور نیست. محافظت برای دورزدن CI خاموش نشود.

انتشار سرویس، deploy، تغییر visibility، اتصال سرویس خارجی یا پیام به شخص/چت دیگر نیازمند دستور مربوط کارفرماست. مجوز متن‌باز و معرفی عمومی بدون انتخاب کارفرما اضافه نشوند.
