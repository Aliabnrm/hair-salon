# درس ریدیزاین حساب و مدیریت سالن

در این تغییر، چهار صفحه ظاهر تازه گرفتند، اما endpoint، احراز هویت و مدل سالن عوض نشد. [تصمیم طراحی و نتیجه بررسی](../design/account-management-redesign.md) مرجع تحویل است.

## چرا UI، hook و API جدا هستند؟

مثال واقعی، تغییر شهر سالن از تهران به شیراز است:

۱. [BusinessFormFields](../../frontend/src/features/salon-management/components/businesses/business-form-fields.tsx) ورودی شهر و label/خطای آن را نمایش می‌دهد. این جزء نمی‌داند نشانی endpoint چیست یا کاربر مالک کدام سالن است؛ فقط مقدار و رویداد تغییر می‌گیرد.

۲. [useBusinessForm](../../frontend/src/features/salon-management/hooks/use-business-form.ts) مقدارها و تفاوت با پاسخ فعلی را نگه می‌دارد. با زدن ذخیره، ورودی را تبدیل می‌کند و از mutation موجود استفاده می‌کند. تعیین اینکه «الان در حال ارسال هستیم» به state و lifecycle React نیاز دارد؛ برای همین hook است.

۳. [businessFormInput](../../frontend/src/features/salon-management/model/business-form-values.ts) یک تابع عادی و خالص است: موبایل فارسی را به رقم انگلیسی و اطلاعات اختیاری خالی را به null تبدیل می‌کند. زمان، شبکه یا React در نتیجه دخالت ندارند؛ ساخت hook برای این تبدیل ضرورتی ندارد. نام/شهر همچنان مطابق قرارداد فعلی به سرور می‌روند و اعتبارسنجی نهایی آنجاست.

۴. [management.api](../../frontend/src/features/salon-management/api/management.api.ts) درخواست PATCH را با version و کلید فعلی می‌فرستد و پاسخ را decode می‌کند. component نیازی به دانستن headerهای HTTP ندارد. سرور نشست، مالکیت و version را بررسی می‌کند؛ تغییر رنگ دکمه هیچ مجوزی ایجاد نمی‌کند.

نتیجه: فرم ساخت و ویرایش از یک UI و یک رفتار استفاده می‌کنند. تفاوت فقط داشتن یا نداشتن Business اولیه و اقدام بعد از پاسخ معتبر است. routeها همان ترکیب‌کننده‌های قبلی ماندند. [استاندارد فرانت](../engineering/frontend-standards.md) و [ADR-002](../architecture/adr/ADR-002-code-organization.md) دلیل این مرزها را توضیح می‌دهند.

## dirty با موفقیت ذخیره فرق دارد

اگر کاربر شهر را تغییر دهد، dirty می‌شود؛ این فقط یعنی مقدار محلی با داده معتبر فرق دارد. موفقیت وقتی نمایش داده می‌شود که پاسخ معتبر API رسیده باشد. نبود تغییر، دکمه ذخیره را غیرفعال می‌کند. در انتظار، فیلدها و ارسال دوباره قفل‌اند.

فرض کنید سرور سالن را ساخته، اما پاسخ شبکه گم شود. نمایش موفقیت قطعی درست نیست؛ ساخت درخواست تازه با کلید تازه هم ممکن است سالن تکراری بسازد. [useManagedMutation](../../frontend/src/features/salon-management/hooks/use-managed-mutation.ts) موجود، همان intent و Idempotency-Key را برای retry نگه می‌دارد. آزمون تازه واقعاً درخواست اول را به سرور می‌رساند و فقط پاسخ را قطع می‌کند؛ سپس یکسان‌بودن کلید و وجود فقط یک سالن را در دیتابیس بررسی می‌کند. API جعلی موفق یا داده نمایشی در محصول اضافه نشده است.

## دریافت نسخه تازه و حفظ ویرایش محلی

پاسخ سرور و state فرم دو چیز متفاوت‌اند. اگر نام را ویرایش کرده‌اید و GET تازه شکست بخورد، این شکست نباید نام تایپ‌شده را پاک کند. [useBusinessSettings](../../frontend/src/features/salon-management/hooks/use-business-settings.ts) آخرین پاسخ معتبر را نگه می‌دارد و فرم تا موفق‌شدن دریافت آگاهانه، بازنشانی نمی‌شود. پاسخ ۴۰۱/۴۰۳/۴۰۴ استثناست: داده خصوصی پنهان می‌شود تا cache محلی جای مجوز سرور ننشیند.

هنگام تغییر هم‌زمان در جای دیگر، version قدیمی رد می‌شود. ورودی محلی باقی می‌ماند؛ کاربر با توضیح روشن تصمیم می‌گیرد دریافت نسخه تازه را انجام دهد یا به ویرایش ادامه دهد. اگر version تازه برابر version قبلی باشد، دریافت موفقِ تأییدشده باز هم باید فرم را بازنشانی کند؛ بنابراین کلید فرم علاوه بر version، revision دریافت موفق را دارد. در شکست GET، revision تغییر نمی‌کند.

## انتخاب ابزار ساده‌تر برای تعامل قابل اتکا

زنانه/مردانه دو radio بومی‌اند؛ رفتار صفحه‌کلید و مفهوم انتخاب را مرورگر فراهم می‌کند. ظاهر سفارشی با همان input پیوند دارد، نه دو دکمه که فقط رنگ‌شان عوض شود. تیک همراه رنگ، انتخاب را روشن می‌کند. ناوبری زیرصفحه‌ها link است و `aria-current` دارد؛ tab نمایشی با نقش نادرست ARIA ساخته نشده است.

برای آدرس از textarea با label مستقل استفاده شد. موبایل LTR است و inputMode/type مناسب دارد. خطا به کنترل متصل است و بعد از ارسال نامعتبر فوکوس به اولین فیلد قابل اصلاح می‌رود. هنگام تایپ هر حرف، فوکوس دوباره جابه‌جا نمی‌شود؛ این نکته در انتخاب dependencyهای effect مهم است.

## چه چیزی را چگونه بررسی کردیم؟

[آزمون رفتار](../../frontend/e2e/account-management-redesign.spec.ts) فرم، خطا، صفحه‌کلید، نسخه، شکست GET، پاسخ گم‌شده و retry را روی API و PostgreSQL واقعی بررسی می‌کند. [آزمون تصویری](../../frontend/e2e/account-management-visual.spec.ts) با حساب آزمایشی مستقل تصاویر چهار مسیر، فهرست خالی و فهرست دارای سالن را در پنج عرض تولید می‌کند. [آزمون مدیریت موجود](../../frontend/e2e/salon-management.spec.ts) همچنان مسیر خدمت/متخصص/ساعت/تعطیلی و مالکیت را بررسی می‌کند.

وجود فایل تست، شاهد موفقیت نیست؛ تعداد و نتیجه اجرای نهایی در سند طراحی ثبت می‌شود. مرور با Chrome جای آزمون موبایل فیزیکی، Safari و screen reader را نمی‌گیرد.
