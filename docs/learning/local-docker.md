# درس اجرای محلی و Docker

تاریخ: ۲۰۲۶-۱۱-۰۳. مثال‌ها از فایل‌های واقعی همین پروژه‌اند. [README](../../README.md) مرجع فرمان‌ها و [گزارش اجرا](../engineering/local-setup-report.md) مرجع نتیجه واقعی است.

## image و container چه فرقی دارند؟

`Dockerfile` دستور ساخت image است؛ image کد و runtime لازم را نگه می‌دارد و container فرایند در حال اجرای آن است. کد روی میزبان وارد کانتینر mount نشده؛ بنابراین ویرایش فایل به‌تنهایی برنامه Docker را عوض نمی‌کند و باید `up --build` اجرا شود. برای توسعه با بازسازی خودکار، روش Node محلی README را انتخاب کنید.

ساخت چندمرحله‌ای یعنی ابزار build در مرحله‌ای استفاده می‌شود و خروجی لازم به مرحله اجرا می‌رود. در target `api`، فقط dependencyهای runtime، dist و migration لازم‌اند؛ در target `frontend`، خروجی standalone، public و static منتقل می‌شوند. کامپایلر TypeScript ابزار اجرای صفحه کاربر نیست.

در ساخت واقعی فرانت، typecheck فایل‌های تست مرورگر نیز اجرا شد و helper دیتابیس backend را لازم داشت. به همین دلیل source بک‌اند در مرحله build فرانت کپی می‌شود؛ این وابستگی آزمایش از runtime فرانت جدا می‌ماند. برای حافظه کمتر، ساخت standalone کانتینری در `frontend/next.config.ts` دو worker دارد؛ این تنظیم تعداد درخواست‌های هم‌زمان کاربران را تعیین نمی‌کند.

## چرا localhost داخل کانتینر اشتباه است؟

هر کانتینر شبکه خودش را دارد. `127.0.0.1:3001` داخل فرانت به همان کانتینر فرانت اشاره می‌کند، پس API را پیدا نمی‌کند. Compose به API نام `api` و به DB نام `postgres` می‌دهد؛ فرانت از `http://api:3001` و API از `postgres:5432` استفاده می‌کند. مرورگر کاربر همچنان فقط `127.0.0.1:3000` را می‌بیند و مسیر هم‌مبدأ `/api/v1` دارد.

API نیز باید روی رابط شبکه کانتینر گوش بدهد؛ به همین دلیل `HOST=0.0.0.0` در Compose داریم. پیش‌فرض `HOST=127.0.0.1` در `backend/src/config/environment.ts` برای اجرای معمول میزبان حفظ شده است. اتصال بیرون دستگاه با انتشار پورت محدود `127.0.0.1:...` در Compose بسته می‌ماند.

## چرا depends_on ساده کافی نیست؟

شروع فرایند PostgreSQL به معنی آماده‌بودن query نیست. `service_healthy` انتظار آماده‌شدن DB را فراهم می‌کند. سپس migration باید با کد موفق خارج شود؛ `service_completed_successfully` مانع شروع API با schema ناقص است. healthcheck API از readiness و healthcheck فرانت از همان readiness پشت proxy استفاده می‌کند.

این زنجیره راه‌اندازی است؛ جای تست کامل محصول یا مانیتورینگ production نیست. برای مثال، HTTP200 صفحه اصلی به‌تنهایی ثابت نمی‌کند ورود یا query DB کار می‌کند.

## داده کجا می‌ماند؟

کانتینر PostgreSQL قابل تعویض است، اما داده در volume نام‌دار `postgres_data` نگه داشته می‌شود. `down` کانتینر را حذف می‌کند و volume باقی است؛ `down --volumes` داده همان محیط را حذف می‌کند. API و migration هر دو همان دیتابیس را می‌بینند. تغییر نام پروژه Compose با `-p` باعث volume جدا می‌شود و ممکن است محیط ظاهراً خالی ببینید؛ این به معنی پاک‌شدن volume قبلی نیست.

## build-time و runtime

rewrite Next هنگام build ساخته می‌شود. در Dockerfile، `BACKEND_ORIGIN` در مرحله ساخت فرانت مشخص می‌شود؛ تنظیم runtime نیز برای دریافت server-side پروفایل استفاده می‌شود. این دو باید هماهنگ باشند. متغیر secret را به ARG تبدیل نکنید؛ ARG برای مقصد غیرحساس شبکه داخلی این پروژه است.

`.dockerignore` با `.gitignore` نقش متفاوت دارد: اولی context ارسالی به Docker و دومی فایل‌های قابل نسخه‌بندی را کنترل می‌کند. خصوصی‌بودن `.env` در Git به‌تنهایی مانع کپی آن به image نمی‌شود؛ به همین دلیل هر دو ignore مهم‌اند. داده و فایل runtime شخصی `work/` هیچ نقشی در clone تازه ندارند.

## چرا Docker محلی با production یکی نیست؟

خروجی فرانت بهینه و production است، اما API محلی development دارد؛ cookie احراز هویت production فقط روی HTTPS معتبر است. HTTPS و secret خصوصی و backup انتخاب‌های محیط انتشارند و با داشتن Dockerfile خودکار حل نمی‌شوند. برای امتحان محلی از فرمان‌های README استفاده کنید و این Compose را بدون تصمیم انتشار روی سرور عمومی اجرا نکنید.
