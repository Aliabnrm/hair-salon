# درس اسپرینت ۵ — داده چه زمانی عمومی می‌شود؟

## هویت، مالکیت و اختیار بررسی

ورود فقط می‌گوید «این درخواست از کدام حساب است؟». در `business-write-transaction.ts`، owner عضویت فعال همان سالن را بررسی می‌کند. reviewer از جدول `reviewer_permissions` می‌آید؛ مالک سالن بودن این اختیار را نمی‌دهد. حتی reviewer اجازه بررسی سالن خودش یا ویرایش خدمات مالک دیگری را ندارد. مخفی‌کردن لینک در UI تنها تجربه کاربر است؛ API مستقل مجوز را کنترل می‌کند.

## ماشین وضعیت

`domain/publication-policy.ts` انتقال‌های مجاز را در یک تابع نگه می‌دارد. درخواست مالک: draft→pending_review؛ تأیید مستقل: pending_review→published؛ تعلیق: published→suspended. هر ترکیب دیگر خطای روشن دارد. مثال ساده: دسترسی reviewer به معنی امکان انتقال مستقیم suspended→published نیست؛ مالک باید اصلاح و درخواست تازه‌ای ارائه کند.

## سه نسخه با سه کاربرد

فرض کنید خدمت A نسخه۲ دارد. ویرایش ساعات متخصص، نسخه خدمت A را عوض نمی‌کند ولی کل محتوای قابل انتشار تغییر کرده است. بنابراین `content_revision` همه تغییرهای سالن را دنبال می‌کند. `publication_version` وضعیت درخواست/تصمیم را کنترل می‌کند؛ `version` فعلی تنظیمات و version خدمت/ساعات نقش قبلی خود را دارند. درخواست، رضایت را به content_revision وصل می‌کند. اگر state عوض شود، نسخه representation تنظیمات نیز به‌روز می‌شود تا ETag قبلی معتبر نماند.

## تراکنش و قفل

در `BusinessWriteTransaction` همه نویسندگان، همان سطر businesses را قفل می‌کنند. اگر مالک قیمت را هم‌زمان با approval تغییر دهد، یکی منتظر دیگری می‌ماند. اگر ویرایش جلوتر باشد، approval کهنه رد می‌شود؛ اگر approval جلوتر باشد، ویرایش پذیرفته‌شده سالن را دوباره draft می‌کند. تنظیمات ممکن است به‌دلیل تغییر version با409 رد شوند و نیاز به بارگذاری تازه داشته باشند. در هیچ ترتیب معتبر، قیمت تازه بدون بررسی منتشر نمی‌شود.

اثر محتوا، state، revision، audit و پاسخ idempotency در یک commit هستند. خطای FK دسته یا version، تمام تغییرها را rollback می‌کند. replay بعد از مجوز و پیش از invalidation تشخیص داده می‌شود؛ تکرار یک ذخیره قدیمی، انتشار جدید را خصوصی نمی‌کند. اگر دسترسی reviewer لغو شده باشد، replay هم403 است.

ترتیب تاریخچه را publication_version تعیین می‌کند، نه فقط created_at. مثال: تراکنش A زودتر شروع شده ولی پشت قفل B منتظر مانده است؛ زمان now() در A قدیمی‌تر است، اما رویدادش بعد از B رخ می‌دهد. نسخه‌ای که زیر قفل افزایش می‌یابد ترتیب درست را حفظ می‌کند. تصمیم reviewer نیز content_revision دیده‌شده را همراه نسخه انتشار می‌فرستد؛ سرور هر دو را بررسی می‌کند.

آمادگی ساعت‌ها فقط وجود برنامه نیست: خدمت۳۰دقیقه‌ای با۱۰دقیقه بافر به یک بازه مشترک۴۰دقیقه‌ای نیاز دارد. دو بازه۲۰دقیقه‌ای جدا، جای آن را نمی‌گیرند. این بررسی قابلیت ارائه کلی خدمت را می‌سنجد؛ هنوز هیچ زمان رزرو آزادی محاسبه نشده است.

## چرا snapshot عمومی موازی نداریم؟

نگهداری «نسخه منتشرشده» در کنار «نسخه در حال ویرایش» نیازمند مدل جدا و تطبیق خدمات/متخصصان/ساعات بود. برای این برش، ویرایش باعث توقف موقت نمایش می‌شود. این تصمیم از نظر UX هزینه دارد، ولی مرز انتشار ساده، قابل توضیح و قابل آزمون می‌ماند. تغییر این سیاست در آینده ADR تازه می‌خواهد.

## DTO عمومی و snapshot خواندن

`public-profile-query.ts` فقط نام، مکان/تماس انتخاب‌شده، خدمات فعال، متخصصان فعال/عمومی و برنامه را به JSON تبدیل می‌کند. entity خصوصی را spread نمی‌کند. دلیل رد، ایمیل مالک، نقش و audit هیچ‌وقت وارد JSON عمومی نمی‌شوند. همه زیرqueryهای همان SELECT، یک snapshot PostgreSQL را می‌بینند؛ بررسی published در یک query و دریافت قیمت جدید در query جدا نداریم. preview مالک و reviewer همین شکل نمایش را با مسیر مجوز خود می‌گیرند.

## نرمال‌سازی و اعتبارسنجی

اعتبارسنجی می‌گوید ورودی مجاز است؟ مثلاً limit=1000 رد می‌شود. نرمال‌سازی، شکل‌های معادل را برای جست‌وجو یکسان می‌کند؛ «نيلوفر» و «نیلوفر» یک کلید می‌شوند. نام نمایشی اصلی حفظ می‌شود. تابع DB و TypeScript با ورودی‌های یکسان تست می‌شوند. ICU در PostgreSQL برای lower یکسان Unicode استفاده می‌شود؛ locale پیش‌فرض C حروفی مانند É را کوچک نمی‌کرد. این اختلاف با آزمون واقعی پیدا شد.

## cursor و index

صفحه بعد به آخرین `(created_at,id)` تکیه دارد؛ timestamp با شش رقم اعشار از PostgreSQL می‌آید و به Date جاوااسکریپت با دقت میلی‌ثانیه تبدیل نمی‌شود. digest فیلتر داخل cursor است؛ cursor جست‌وجوی قبلی را با شهر دیگری نمی‌توان استفاده کرد. digest امضای امنیتی نیست؛ هر صفحه مستقل فقط published را query می‌کند. index جزئی ترتیب فهرست منتشرشده را پشتیبانی می‌کند. جست‌وجوی substring برای دیتاست فعلی است؛ این اسپرینت ادعای کارایی در میلیون‌ها سالن ندارد.

## state در مرورگر

در `use-discovery-filters.ts`، شهر/دسته/جست‌وجو در URL هستند؛ پاسخ API، server state است؛ متن در حال تایپ و بازبودن پنجره، UI state محلی‌اند. تایپ350ms مکث دارد. `useRemote` درخواست قبلی را abort می‌کند و sequence پاسخ دیررس را نادیده می‌گیرد. خطای شبکه با فهرست خالی اشتباه نمی‌شود؛ back/forward فیلتر قابل اشتراک را برمی‌گرداند. hook برای این هماهنگی stateful لازم است؛ `formatPrice` تابع خالص است و hook نیست.

قیمت‌ها integer IRR هستند. مثلاً ۲٬۵۰۰٬۰۰۰ ریال، دقیقاً۲۵۰٬۰۰۰ تومان است؛ صفر هم قیمت معتبر خدمت است. ساعات هفتگی «وقت آزاد» نیستند و در UI این تفاوت روشن است.

فایل‌های بالا نسبت به `backend/src/modules/salon-management/` یا feature متناظر فرانت هستند؛ [درخت دقیق](../architecture/sprint-05-structure.md) و [گزارش اجرا](../planning/sprints/sprint-05-report.md) مسیرهای کامل و شاهد آزمون را دارند.
