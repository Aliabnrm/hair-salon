# روش همکاری و یادگیری
تاریخ ۲۰۲۶-۱۰-۲۹؛ تیم: کارفرما و دستیار. بک‌اند NestJS انتخاب شده؛ آموزش معماری و مفاهیم مهم بک‌اند بخشی از تحویل است.

## چرخه هر اسپرینت
۱. دستیار طرح کوتاه شامل هدف، دامنه داخل/خارج، وابستگی، تصمیم فنی، معیار پذیرش، تست و مفاهیم آموزشی ارائه می‌کند.
۲. کارفرما طرح را تأیید یا اصلاح می‌کند؛ تا قبل تأیید، فقط بررسی و مستندسازی انجام می‌شود.
۳. پس از تأیید، دستیار پرامپت اجرایی مستقل و قابل استفاده همان اسپرینت را می‌نویسد و نشان می‌دهد؛ شامل زمینه، اسناد مرجع، کارها، محدودیت‌ها، معیارها و روش تحویل.
۴. سپس همان محدوده پیاده‌سازی و بررسی می‌شود. تأیید محدوده مجوز اجرای همان اسپرینت است؛ تأیید دوباره برای کارهای عادی داخل آن لازم نیست. اگر کارفرما صریحاً فقط پرامپت بخواهد، اجرا انجام نمی‌شود. تغییر مهم دامنه یا تصمیم مصوب دوباره مطرح می‌شود.
۵. گزارش پایان: چه تغییر کرد و چرا، چه آزمونی واقعاً اجرا شد و نتیجه چه بود، چه محدودیتی مانده، مسیر اجرای محلی و نمایش قابلیت.
۶. آموزش: مسئله→مفهوم با زبان ساده→مسیر واقعی درخواست در کد→دلیل انتخاب→خطای رایج→تمرین کوچک اختیاری.
۷. مرور کارفرما و پیشنهاد اسپرینت بعد؛ شروع اسپرینت بعدی نیازمند تأیید خودش است.

اسپرینت ۱ تکمیل و گزارش/درس آن ثبت شد. کارفرما محدوده اسپرینت ۲ را تأیید کرد؛ [طرح دقیق](sprints/sprint-02-plan.md) و [پرامپت](../prompts/sprint-02.md) آماده‌اند و هنوز اجرای DB انجام نشده است. ایجاد Git، commit/push و PR روی ریپوی معرفی‌شده نیز مجاز شدند؛ [روند Git](../engineering/git-workflow.md) جزئیات را مشخص می‌کند. هیچ پیام یا کاری خودکار به چت دیگری ارسال نمی‌شود؛ اجرای اسپرینت در همین پروژه است مگر کارفرما خلافش را بخواهد.

## شیوه یادگیری
هر اسپرینت حداکثر چند مفهوم اصلی و مرتبط با کد واقعی معرفی کند. اسم الگوها جای توضیح مسئولیت را نگیرد. استانداردهای ساده‌ای مانند مسئولیت واحد، تزریق وابستگی و جداسازی HTTP از قانون کسب‌وکار ابتدا در مثال واقعی دیده شوند. تمرین اختیاری است و مانع تکمیل قابلیت مصوب نیست.

آموزش فارسی؛ نام فایل، متغیر و API انگلیسی. هر گزارش آموزشی در docs/learning/ ثبت و به فایل‌ها و تست‌های واقعی همان اسپرینت ارجاع دهد. ادعای آموزش عملی یا قبولی آزمون قبل از اجرا ممنوع.

## کیفیت و بازبینی
هر تغییر کوچک و قابل فهم باشد. اجزای مشترک فقط پس از نیاز واقعی استخراج شوند؛ interface برای هر کلاس، repository عمومی همه‌کاره و abstraction تزئینی ساخته نشود. امنیت و صحت داده از ابتدا همراه قابلیت‌اند. اصل SOLID در کاهش مسئولیت و وابستگی سنجیده شود، نه تعداد فایل‌ها.

تعریف Done: معیارهای اسپرینت اثبات، build/checkهای متناسب پاس، خطاها روشن، مستند اجرای محلی و تصمیم‌ها به‌روز، گزارش تغییر و آموزش ارائه شده؛ موارد اجرا‌نشده صریح اعلام شوند. زمان ثابت اسپرینت فعلاً نداریم؛ ابتدا ریتم همکاری و زمان مرور کارفرما را اندازه می‌گیریم.
