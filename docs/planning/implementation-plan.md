# برنامه توسعه پیشنهادی پس از تأیید
**این برنامه مجوز شروع کدنویسی نیست.** برش‌های S زیر نقشه وابستگی محصول‌اند و معادل شماره اسپرینت نیستند. برنامه جاریِ اسپرینت‌ها و اولویت آموزشی در [sprint-plan](sprint-plan.md) است؛ ترتیب این سند تابع آن برنامه می‌شود. هر slice یک مسیر قابل استفاده از UI تا سرور و DB تحویل می‌دهد. فایل‌ها/ماژول‌های زیر نام‌های پیشنهادی‌اند؛ در این مرحله ایجاد نشده‌اند. تیم کارفرما و دستیار مشخص است؛ زمان‌بندی پس از شناخت ظرفیت همکاری،دامنه خدمات و ADR تعیین می‌شود.

تعریف Done مشترک: demo مسیر اصلی و حالت شکست، معیارهای پذیرش مرتبط، مجوز سرور و tenant، migration بازبینی‌شده و سازگار، تست متناسب ریسک، عدم PII در log، حالت loading/empty/error و RTL، به‌روزرسانی traceability و سند تغییر. امنیت و اعلان پایه از اولین برش همراه قابلیت‌اند؛ به پایان پروژه موکول نمی‌شوند. هر ردیف را به PRهای کوچکِ domain/DB، use-case/API و UI/test بشکنیم، اما slice فقط با تکمیل مسیر انتهابه‌انتها Done است.

## تسک‌های کوچک و قابل بازبینی
- برای S4: مشخصات invariant و test fixture DB؛ migration allocation/constraint؛ create use-case و idempotency؛ endpoint و نگاشت conflict؛ UI انتخاب/تأیید با حفظ key در retry؛ worker تأیید و dashboard خطا؛ demo رقابت/timeout. پایان هر تسک شاهد مستقل و تغییر محدود داشته باشد.
- برای S5/S6: ابتدا قواعد version و transaction، سپس routeها و UI؛ تغییرات برنامه و block همان سرویس قفل را مصرف کنند. قابلیت تازه نباید مسیر رزرو موازی بدون invariant بسازد.
- برای S9: اجرای تست‌ها/بررسی security و ثبت شواهد، تمرین restore، آزمون شبکه و SMS، آموزش سالن، سپس پایلوت محدود. افزودن قابلیت P1 در این برش ممنوع مگر scope تغییر ثبت‌شده باشد.

ترتیب اعلان و ادمین عمدی است: بررسی انتشار پیش از بازارگاه و تأیید SMS از اولین رزرو وجود دارد؛ S8 عملیات پیشرفته‌تر را کامل می‌کند. dependencyهای مشترک infra با مسیر کاربری هر slice تحویل می‌شوند، نه یک انبوه زیرساخت بدون رفتار قابل مشاهده.

تغییر نیاز: request→اثر بر FR/NFR/story→مدل/API/تست/هزینه→پیشنهاد جایگزین→تأیید تصمیم مهم→به‌روزرسانی ADR/trace→توسعه slice کوچک. با ورود بیعانه یا خدمات چندمرحله‌ای، این برنامه باید قبل از شروع/ادامه بخش مربوط بازنویسی شود.
