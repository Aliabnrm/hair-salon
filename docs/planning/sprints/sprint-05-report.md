# گزارش اجرای اسپرینت ۵ — کاتالوگ واقعی و انتشار بررسی‌شده

تاریخ: ۲۰۲۶-۱۱-۰۲. مرجع محدوده: [پرامپت مصوب](../../prompts/sprint-05.md) و [طرح](sprint-05-plan.md). شاخه محلی `feat/sprint-05-public-catalog` بر مبنای `dev/origin/dev` به‌روز در `c8bcaf6` است. تغییرهای مستند موجود کارفرما در شروع حفظ شدند. هیچ commit، push، PR، merge، deploy یا اعطای دسترسی به حساب واقعی انجام نشد.

## خروجی قابل استفاده

مسیر کامل مالک→تکمیل اطلاعات→پیش‌نمایش خصوصی→رضایت همان نسخه→درخواست→بررسی مستقل→نمایش ناشناس پیاده شد. دسته‌ها از دیتابیس می‌آیند؛ معرفی کوتاه اختیاری و انتخاب صریح نمایش متخصص اضافه شدند. آمادگی واقعی سرور، نقص و لینک بخش اصلاح را به مالک می‌دهد. برنامه مشترک سالن/متخصص باید برای مدت خدمت همراه با بافرها کافی باشد؛ بازه‌های جدا جمع نمی‌شوند.

درخواست، انصراف، توقف نمایش، تأیید، رد و تعلیق همراه تاریخچه خصوصی وجود دارند. ویرایش تازه و موفق هر بخش مؤثر، درخواست pending یا انتشار را اتمیک باطل می‌کند. suspended با ذخیره عادی منتشر نمی‌شود و ارسال دوباره نیازمند اصلاح محتواست. replay یا rollback انتشار تازه را باطل نمی‌کند. تأیید هم‌زمان با ویرایش و تصمیم‌های رقیب زیر قفل همان سالن کنترل می‌شوند.

کشف به API واقعی وصل است: جست‌وجوی فارسی روی نام سالن و خدمات، فیلتر نوع/دسته/شهر/محله، صفحه بعد در URL، بازگشت/جلو، debounce و جلوگیری از پاسخ دیررس. شهرها فقط از سالن‌های منتشرشده‌اند؛ دیتابیس خالی، سالن نمونه ندارد. قیمت «از» در سرور برای دسته انتخاب‌شده محاسبه و در رابط دقیق به تومان تبدیل می‌شود؛ صفر واقعی معتبر است. ترکیب جست‌وجوی یک خدمت با دسته خدمتی دیگر، قیمت null تولید نمی‌کند.

پروفایل مشترک عمومی/پیش‌نمایش، خدمات، متخصصان عمومی، نشانی، تماس و ساعات واقعی را نمایش می‌دهد. اطلاعات خصوصی و متخصص مخفی وارد DTO عمومی نمی‌شوند. صفحه غیرعمومی 404 واقعی و metadata ثابت دارد؛ API و دریافت عمومی Next بدون cache ماندگار هستند. رزرو، وقت آزاد، عکس نمونه، امتیاز و پرداخت اضافه نشده‌اند. ورود ایمیل/رمز و نشست فعلی حفظ شدند؛ تأیید ایمیل/reset/MFA افزوده نشدند.

## نتیجه بررسی واقعی

محیط: Node24.22.2، pnpm12.16.1، PostgreSQL17.11 محلی روی55432؛ مرورگر Chrome از طریق Playwright. نسخه ابزارها و lockfile حفظ شدند. نصب `pnpm install --frozen-lockfile` انجام شد.

فرمان نهایی ریشه، `pnpm run check` با TEST_DATABASE_URL اختصاصی و `PLAYWRIGHT_CHANNEL=chrome` اجرا شد. URL و secret در خروجی ثبت نشدند. در این دستگاه helper محلی ignored، همین فرمان را با تنظیم خصوصی تست اجرا می‌کند:

```sh
export PATH="$PWD/work/tools/bin:$PWD/work/runtime/node-v24.22.2-darwin-arm64/bin:$PATH"
PLAYWRIGHT_CHANNEL=chrome node work/run-sprint-05-check.mjs run check
```

تست PG شامل fresh migration، ارتقای داده‌دار اسپرینت۴، rerun، مالک دیگر، reviewer مستقل/self-review، لغو اختیار قبل replay، نسخه محتوای اشتباه، رضایت، rollback، audit دقیقاً یک‌بار، رقابت approval با مشخصات/خدمت/متخصص/ساعت/استثنا، تصمیم‌های رقیب، تعلیق، خواندن عمومی سازگار، جست‌وجوی فارسی و cursor با اختلاف یک میکروثانیه است. CLI grant/revoke فقط در DB موقت با حساب کنترل‌شده و منع production آزموده شد.

تست مرورگر انتشار از فرم مالک و reviewer و داده واقعی DB استفاده می‌کند؛ مسیر موفق با mock جایگزین نشده است. ویرایش پس از انتشار، رد/اصلاح/ارسال مجدد، تعلیق، خروج و لغو اختیار نیز بررسی شدند. عرض‌های۳۲۰/۳۶۰/۳۹۰/۴۳۰ و دسکتاپ، URL/back/forward، صفحه‌کلید، شبکه قطع، پاسخ دیررس و متن۲۰۰٪ پوشش دارند. تب فعال مدیریت بعد تغییر عرض نیز در دید باقی می‌ماند. این بررسی ادعای audit کامل دسترس‌پذیری نیست.

شکست‌های پیش از نتیجه نهایی: Chromium همراه Playwright نصب نبود؛ از fallback مستند Chrome استفاده شد. build یک بار خطای نوع `Node.remove` در کد تست داشت که با API درست DOM اصلاح شد. در یک اجرای کامل، دو تست مرورگر timeout داشتند؛ همان دو در مجموعه متمرکز۸تایی و اجرای کامل بعدی بدون تغییر assertion موفق شدند. علت قطعی آن timeoutها احراز نشد؛ نتیجه نهایی از اجرای کامل موفق تازه است.

تست تصویری قدیمی، فایل‌های شواهد ریدیزاین اسپرینت۴ را بازنویسی می‌کرد. تصاویر تاریخی به نسخه پیش از اجرای ما برگردانده شدند و مقصد ثبت فعلی به `work/account-management-redesign/current/` منتقل شد؛ assertهای قبلی حفظ شدند. در پایان، پوشه موقت browser و اتصال/DB اسپرینت۵ باقی نماند. چهار DB تست قدیمی بدون schema اسپرینت۵ و بدون اتصال فعال شناسایی شدند و چون متعلق به این اجرا نبودند تغییر نکردند. تصاویر انتشار فعلی در `frontend/test-results/` و لاگ‌های این دستگاه در `work/sprint-05-*.log` هستند و وارد Git نمی‌شوند.

## شواهد query و بازبینی

تست `publication.integration-spec.ts` همان `publicSalonsSql` واقعی را با EXPLAIN ANALYZE/BUFFERS بررسی کرد. دیتاست کنترل‌شده۳سالن منتشرشده و۶خدمت داشت. plan از `public_businesses_order_idx` و زیرquery کمینه قیمت از `services_list_idx` استفاده کرد؛۳ردیف،۸shared hit و۰read در خروجی ثبت شد. اجرای مشاهده‌شده حدود۲میلی‌ثانیه بود. این نمونه کوچک، تست بار یا شاهد عملکرد در مقیاس واقعی نیست.

فهرست و صفحه‌بندی یک query اصلی دارند؛ join خدمات سالن را تکرار نمی‌کند. زیرqueryهای پروفایل در همان statement اجرا می‌شوند، نه درخواست شبکه جدا برای هر خدمت. جست‌وجوی substring و دریافت موقعیت‌ها برای دامنه فعلی است؛ عملکرد و اندازه پاسخ موقعیت‌ها با رشد داده نیازمند اندازه‌گیری است. Redis/Elasticsearch اضافه نشدند.

مرز import، whitelist DTO و کلاینت، مدیریت خطا، state/version، اثر rollback/replay و داده حساس مرور شدند. import نمونه فقط در فایل‌های تاریخی/تست باقی است و از routeهای runtime قابل دسترسی نیست. migrationهای0000..0003 و snapshotهایشان تغییر نکردند. تصاویر تاریخی، dependencyها و تنظیمات auth موجود حفظ شدند.

## migration توسعه و حفظ داده قبلی

قبل از migration، از تمام ستون‌های قبلی۱۵جدول app، شمارش و اثرانگشت مرتب‌شده ثبت شد؛ مقادیر حساس چاپ نشدند. سپس `pnpm run db:migrate`، مقایسه، اجرای دوباره migration و مقایسه دوباره انجام شدند. **در هر دو مقایسه، تمام شمارش‌ها و اثرانگشت ستون‌های قبلی یکسان بودند.**

داده حفظ‌شده شامل۲کاربر،۲credential رمز،۲نشست،۱سالن،۱عضویت،۱خدمت،۲متخصص،۱تخصیص،۴بازه سالن،۶audit و۶نتیجه idempotency است. جدول‌های خالی نیز یکسان ماندند. داده توسعه reset یا با سالن تست پر نشد.

پس از ارتقا: سالن موجود draft، همه متخصصان قدیمی مخفی، دسته خدمت قدیمی null، تعداد reviewer واقعی فعال۰ و دسته‌های مرجع۷ است. تنها افزودن‌های مصوب migration اعمال شدند. اثر انگشت مبنا در `work/sprint-05-data-before.json` ثبت است؛ دو مقایسه موفق migration پیش از راه‌اندازی سرور انجام شدند. مقایسه بعد از smoke در `work/sprint-05-data-after-smoke.json` است:۱۴جدول پایدار همچنان یکسان‌اند؛ جدول موقت auth_attempt_buckets طبق رفتار معمول محدودکننده نرخ، با درخواست‌های عمومی به‌روز و ورودی‌های منقضی آن پاک شدند. این تغییر بعد از migration و ناشی از اجرای برنامه است.

## مسیر امتحان دستی

1. فرانت۳۰۰۰ و API۳۰۰۱ و PostgreSQL۵۵۴۳۲ را طبق [README](../../../README.md) اجرا کنید؛ از مبدأیی استفاده کنید که در AUTH_ALLOWED_ORIGINS محلی تعریف شده است.
2. وارد حساب مالک شوید؛ مدیریت سالن→مشخصات/خدمات/متخصصان/ساعات را تکمیل کنید. خدمت قدیمی نیازمند انتخاب دسته است و متخصص باید صریحاً عمومی شود.
3. تب «انتشار»→نقص‌ها را برطرف کنید→پیش‌نمایش→رضایت→ارسال درخواست.
4. برای reviewer یک حساب **مستقل و موجود** معرفی کنید؛ فقط در development/test و پس از build، UUID واقعی را در فرمان زیر جایگزین کنید:

```sh
NODE_ENV=development pnpm --filter @hair-salon/api exec node dist/database/reviewer-permission.js grant USER_UUID "دلیل اعطای اختیار"
NODE_ENV=development pnpm --filter @hair-salon/api exec node dist/database/reviewer-permission.js revoke USER_UUID "دلیل لغو اختیار"
```

5. در مرورگر جدا با همان reviewer وارد شوید؛ حساب→بررسی درخواست‌های انتشار→پیش‌نمایش و تصمیم. مالک حق تأیید سالن خودش را ندارد.
6. ناشناس کاوش و لینک `/salons/[businessId]` را باز کنید؛ پس از ویرایش مالک یا تعلیق، سالن عمومی پنهان و لینک مستقیم404 می‌شود.

در smoke محلی، صفحه اصلی، readiness، دسته‌ها و فهرست واقعی200، دسترسی ناشناس reviewer برابر401 و سالن غیرعمومی404 بودند. فهرست توسعه فعلاً خالی است چون هیچ سالن موجودی خودکار منتشر نشده است.
