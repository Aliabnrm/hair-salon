UI و state/network جدا و Design System موجود حفظ شده؛ dependency تازه‌ای اضافه نشد. [ADR-015](../../architecture/adr/ADR-015-salon-operations.md)، [رابط۹](../../architecture/sprint-09-ui.md) و [درس۹](../../learning/sprint-09.md).

migration0007 افزایشی، با PK مستقل allocation و XOR منبع appointment/block، exclusion مشترک، قید ledger و تاریخچه immutable است. migrationهای قبلی بازنویسی نشدند. مالکیت پیش و پس قفل/replay بررسی می‌شود؛ clock پس از قفل خوانده می‌شود. نقش مستقل متخصص/پذیرش، پیامک، درآمد، auth، CRM، جابه‌جایی مالک و اسپرینت۱۰ وارد این برش نشده‌اند.

## وضعیت بررسی

فرمان `PLAYWRIGHT_CHANNEL=chrome node work/run-sprint-07-check.mjs run check` با کد خروج صفر پایان یافت. runner نادیده‌گرفته‌شده فقط env دیتابیس اختصاصی تست را به `pnpm run check` می‌دهد. build هر دو workspace، typecheck، lint و format:check و همه۳۹۵تست موفق بودند:

| دسته             | تعداد موفق |
| ---------------- | ---------- |
| unit بک‌اند      | ۱۲۲        |
| unit فرانت       | ۴۹         |
| HTTP و OpenAPI   | ۵۶         |
| PostgreSQL واقعی | ۱۱۵        |
| مرورگر Chrome    | ۵۳         |

شواهد مهم: مرز دقیق completed/no_show و رد زودهنگام، اصلاح با دلیل/نسخه و حفظ snapshot/allocation، recheck ساعت پس از قفل، race دو نتیجه، رزرو/مسدودی و جابه‌جایی/مسدودی، replay هم‌زمان، مجوز سالن/CSRF/ورودی اضافه، rollback و قید مستقیم orphan/XOR/release/history. تست upgrade به‌صورت matrix از journal دقیق اسپرینت۷ و۸ اجرا شد؛ ستون‌های قبلی receipt/allocation/event/intent و hashهای migration قبلی حفظ شدند. ستون‌های جدید با داده قدیمی مقایسه کاذب نشدند.

مرورگر مسیر ثبت/اصلاح نتیجه مالک→مشاهده مشتری، روز/هفته/فیلتر/خلاصه، مسدودی→حذف ظرفیت عمومی→رفع→بازگشت ظرفیت و پاسخ گم‌شده پس از commit→reload→همان منبع را تأیید کرد. عرض۳۲۰/۳۶۰/۳۹۰/۴۳۰/۱۲۸۰ و متن۲۰۰٪ بدون overflow بررسی شدند؛ تست‌های کیبورد، حفظ داده هنگام خطای refresh، privacy و جریان‌های قبلی نیز در check کامل موفق بودند. تصویر فرم موبایل در `work/sprint-09-screens/block-form-390.png` بازبینی شد؛ فرم داخل AppShell اسکرول دارد و عملیات با کلیک واقعی آزموده شدند.

در بازبینی، SQL حذف اشغال خود نوبت به `IS DISTINCT FROM` تغییر کرد تا block دارای appointment_id=null هنگام جابه‌جایی از busy حذف نشود. قید release_reason نیز صریحاً NULL را رد می‌کند؛ CHECK با عبارت nullable به‌تنهایی کافی نبود. تست‌های تازه این دو مورد را پوشش می‌دهند. assertionهای فهرست مسیر OpenAPI، شمار migrationها و متن empty قبلی با قرارداد جدید همگام شدند. اجرای نخست مرورگر با بازسازی هم‌زمان dist تداخل داشت؛ اجرای ترتیب‌دار نهایی موفق است. نتیجه جدول بالا متعلق به آخرین اجرای کامل پس از اصلاح‌هاست.

## اجرای محلی و محدودیت‌ها

پیش از migration توسعه، سرویس‌های محلی همین پروژه متوقف و backup با دسترسی۰۶۰۰ در `work/sprint-09-local-before.dump` گرفته شد. migration واقعی اجرا شد؛ تعداد/اثر انگشت نوبت‌ها، همه فیلدهای رویدادهای موجود و ستون‌های پیشین allocation/intent قبل و بعد یکسان ماندند. فیلد id تازه allocation و block_id افزوده شدند؛ هیچ نوبت واقعی برای آزمایش تغییر نکرد. شاهد بدون داده شخصی در `work/sprint-09-local-result.json` است؛ فایل‌های خصوصی work وارد Git نمی‌شوند.

نسخه جدید روی `http://localhost:3000` و API پورت۳۰۰۱ اجراست. بررسی زنده، HTTP200 فرانت و readiness، وجود endpointهای۹ در OpenAPI جاری و رد مهمان با۴۰۱ روی overview را تأیید کرد؛ شاهد `work/sprint-09-live-result.json`. typeهای Next با `next typegen` تولید شدند؛ فایل تولیدی دستی ویرایش نشد.

CI راه دور، Docker، بار production، تست شبکه اپراتورهای ایران و deploy در این تحویل اجرا نشده‌اند. تاریخچه block شامل ایجاد و یک رفع تغییرناپذیر است؛ ویرایش تکرارشونده یا بازفعال‌کردن block نداریم. نمای هفته یک فهرست۷روزه از تاریخ انتخابی است؛ realtime/drag/drop/نمای ستونی اضافه نشده است. خلاصه از وضعیت ثبت‌شده محاسبه می‌شود و گزارش درآمد نیست.

همه تغییرها محلی و ثبت‌نشده روی `feat/sprint-09-salon-operations` هستند؛ مرز import، تکرار، خطا، داده حساس و diff بررسی شدند. commit/push با کارفرماست و اسپرینت۱۰ آغاز نشده است.

## پذیرش دستی

پنل سالن→نوبت‌ها→انتخاب روز/فهرست هفته و فیلتر متخصص/وضعیت. یک نوبت گذشته را باز کن→ثبت نتیجه مراجعه→تأیید انجام‌شده/عدم حضور. اصلاح با دلیل در همان صفحه است؛ مشتری همان تاریخچه را می‌بیند. نوبت آینده را برای تست نتیجه دست‌کاری نکن؛ سرور عمداً ثبت زودهنگام را رد می‌کند.

در دفتر→مسدودکردن زمان→متخصص، روز و ساعت آینده و دلیل→تأیید. اگر با نوبت دیگری تداخل باشد درخواست رد و نوبت قبلی حفظ می‌شود. در مرورگر مشتری زمان اشغال‌شده دیگر پیشنهاد نمی‌شود. رفع با دلیل، سابقه را نگه می‌دارد و ظرفیت را آزاد می‌کند.
