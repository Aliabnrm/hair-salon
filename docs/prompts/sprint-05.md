ساختار هدف در feature موجود:


قانون واحد انتشار و آمادگی نباید بین UI، Controller و adapter با پیاده‌سازی‌های متفاوت تکرار شود.

## ۵. آمادگی انتشار و رضایت مالک

آمادگی انتشار باید در سرور محاسبه شود و حداقل این موارد را بررسی کند:

- مالک فعال همان سالن.
- نام، نوع، شهر، نشانی و موبایل عمومی معتبر.
- حداقل یک خدمت فعال.
- دسته معتبر برای همه خدماتی که قرار است عمومی نمایش داده شوند.
- برای هر خدمت عمومی، حداقل یک متخصص فعال و قابل نمایش عمومی با تخصیص همان سالن.
- برنامه هفتگی معتبر سالن.
- برنامه معتبر متخصصان ارائه‌دهنده خدمات عمومی و حداقل تقاطع کاری لازم با سالن.

از قواعد بازه و تقاطع موجود استفاده کن؛ موتور availability یا slot نساز. تعطیلی موقت به معنی حذف امکان معرفی سالن نیست.

خروجی آمادگی شامل موارد مشخص و قابل اصلاح باشد:

- کد نقص.
- بخش و فیلد مربوط.
- شناسه خدمت/متخصص مرتبط در صورت نیاز.
- توضیح فارسی قابل فهم.

فرانت از این داده‌ها لینک اصلاح بسازد. درصد تکمیل یا چک‌لیست نمایشیِ مستقل از سرور نساز.

پیش‌نمایش خصوصی همان projection قابل انتشار را نمایش دهد. نقص‌ها نیز بیرون از component عمومی، روشن نشان داده شوند.

در درخواست انتشار، مالک صریحاً تأیید کند که اطلاعات مشخص‌شده، از جمله نشانی، موبایل عمومی، قیمت‌ها و نام‌های نمایشی انتخاب‌شده، برای نمایش عمومی ارائه شده‌اند. رضایت به نسخه محتوای درخواست متصل و ثبت شود.

تأیید ایمیل در این قواعد وجود ندارد.

## ۶. چرخه انتشار

وضعیت اصلی سالن فقط یک مرجع معتبر داشته باشد:

| وضعیت            | معنی                                |
| ---------------- | ----------------------------------- |
| `draft`          | خصوصی، قابل تکمیل                   |
| `pending_review` | درخواست بررسی نسخه مشخص             |
| `published`      | قابل مشاهده در کاتالوگ عمومی        |
| `suspended`      | نمایش عمومی توسط reviewer متوقف شده |

انتقال‌های مجاز:

- مالک: `draft → pending_review` پس از آمادگی و رضایت.
- مالک: انصراف از `pending_review → draft`.
- مالک: توقف نمایش `published → draft`.
- reviewer مجاز: `pending_review → published`.
- reviewer مجاز: رد درخواست `pending_review → draft` با دلیل.
- reviewer مجاز: `published → suspended` با دلیل.
- مالک: پس از اصلاح، ارسال درخواست تازه از `suspended → pending_review`.

مالک نمی‌تواند با PATCH عمومی، state یا نتیجه بررسی را تعیین کند. reviewer نیز مسیر مستقیمی برای بازگرداندن suspended به published بدون درخواست و بررسی معتبر تازه نداشته باشد.

### سیاست تغییر اطلاعات

برای این اسپرینت، snapshot عمومی موازی نساز.

هر mutation تازه و موفق در مشخصات سالن، خدمات، متخصصان/تخصیص‌ها، نمایش عمومی متخصص، ساعات یا استثناهای کاری، یک تغییر محتوای کاتالوگ محسوب شود:

- در `published`: تغییر و بازگشت به `draft` در یک transaction.
- در `pending_review`: درخواست قبلی نامعتبر و سالن به `draft` برگردد.
- در `draft`: خصوصی باقی بماند.
- در `suspended`: تعلیق با ویرایش عادی برداشته نشود.

این سیاست محافظه‌کارانه عمداً برای تمام مسیرهای یادشده یکسان است؛ UI پیش از ذخیره، پیام متناسب بدهد.

عملیات ناموفق، rollback یا replay موفق درخواست قبلی نباید revision را دوباره افزایش دهد یا انتشار تازه‌ای را لغو کند.

سابقه درخواست‌ها، رد، تأیید، انصراف و تعلیق حفظ شود. دلیل رد و تعلیق برای مالک قابل مشاهده و برای عموم مخفی باشد.

## ۷. نسخه، transaction و idempotency

نسخه فعلی هر خدمت/متخصص/فرم را با نسخه کل محتوای کاتالوگ اشتباه نگیر.

مدلی مشخص برای این دو مفهوم داشته باش:

1. revision محتوای کاتالوگ که تغییرات مؤثر همه مسیرهای مرتبط را پوشش می‌دهد.
2. نسخه منبع انتشار برای کنترل هم‌زمانی درخواست‌ها و تصمیم‌ها.

در درخواست انتشار، revision محتوای ارسال‌شده ثبت شود. تأیید فقط برای همان درخواست و همان revision معتبر باشد.

قواعد ضروری:

- تمام writeهای مرتبط، قفل مشترک و ترتیب ثابت روی سالن داشته باشند.
- هنگام approval، مجوز reviewer، وضعیت فعلی، درخواست جاری، نسخه و آمادگی دوباره داخل transaction بررسی شوند.
- بررسی قبلی UI یا GET اولیه، مجوز approval نیست.
- تغییر داده، وضعیت انتشار، revision، سابقه تصمیم، audit و نتیجه idempotency اتمیک باشند.
- پاسخ نهایی و ETag با وضعیت commitشده هماهنگ باشند.
- اگر تغییر state روی representation تنظیمات اثر می‌گذارد، نسخه مرتبط نیز درست به‌روز شود.
- فیلد نسخه موجود را بی‌اطلاع بازتعریف نکن.

از زیرساخت فعلی `BusinessWriteTransaction` و قرارداد کلید درخواست استفاده کن. برای reviewer، مسیر مجوز صریح و مستقل ایجاد کن؛ flagهایی مانند `skipAuthorization` نساز.

ترتیب درخواست تکراری:

**احراز و مجوز فعلی ← replay معتبر ← بررسی نسخه/وضعیت/آمادگی ← تغییر اتمیک**

replay نباید اثر دوم، audit دوم یا تغییر revision دوم ایجاد کند. مجوز لغوشده حتی برای replay هم معتبر نیست.

نسخه ناموجود، نسخه کهنه، کلید تکراری با payload متفاوت و نتیجه منقضی طبق قرارداد فعلی پاسخ داده شوند.

## ۸. دسترسی reviewer

دسترسی reviewer مستقل از مالکیت سالن باشد.

- از ثبت‌نام، ایمیل کاربر، ورودی مرورگر یا داشتن سالن، reviewer ساخته نشود.
- نقش از DB و برای هر درخواست بررسی شود.
- در تصمیم‌های نوشتنی، دسترسی داخل transaction دوباره بررسی شود.
- reviewer حق بررسی یا تأیید سالن متعلق به خودش را نداشته باشد.
- صرف داشتن نقش reviewer، مجوز تغییر خدمات و مشخصات سالن دیگران نیست.
- اطلاعات draftهایی که هرگز برای بررسی ارائه نشده‌اند، وارد صف بررسی نشوند.

برای اعطا و لغو دسترسی، CLI محدود و مستند بساز:

- دریافت User ID موجود و دلیل عملیات.
- بدون endpoint عمومی اعطای نقش.
- بدون انتخاب خودکار اولین حساب یا حساب با ایمیل خاص.
- ثبت سابقه محدود اعطا/لغو.
- در محدوده این اسپرینت، اجرای CLI به محیط development/test محدود باشد.
- حساب واقعی reviewer را کارفرما معرفی می‌کند؛ خودسرانه به حساب واقعی دسترسی نده.
- تست و demo خودکار از حساب‌های کنترل‌شده در DB موقت استفاده کنند.

رابط reviewer فقط شامل صف، جزئیات لازم، پیش‌نمایش و تصمیم‌های همین قابلیت باشد؛ پنل ادمین همه‌کاره نساز.

## ۹. قرارداد HTTP

پیشوند `/api/v1` و envelope فعلی حفظ شوند.

مسیرهای هدف:

| مسیر                                                    | کاربرد                                        |
| ------------------------------------------------------- | --------------------------------------------- |
| `GET /catalog/categories`                               | دسته‌بندی مرجع                                |
| `GET /catalog/locations`                                | شهر/محله‌های دارای سالن منتشرشده              |
| `GET /catalog/salons`                                   | جست‌وجو و صفحه‌بندی عمومی                     |
| `GET /catalog/salons/{businessId}`                      | پروفایل عمومی                                 |
| `GET /businesses/{businessId}/publication`              | وضعیت، نسخه انتشار و نقص‌های آمادگی برای مالک |
| `GET /businesses/{businessId}/preview`                  | پیش‌نمایش خصوصی مالک                          |
| `POST /businesses/{businessId}/publication/requests`    | درخواست انتشار با رضایت و نسخه                |
| `POST /businesses/{businessId}/publication/withdrawals` | انصراف یا توقف نمایش توسط مالک                |
| `GET /review/access`                                    | قابلیت reviewer برای حساب فعلی                |
| `GET /review/businesses`                                | صف محدود و صفحه‌بندی‌شده بررسی                |
| `GET /review/businesses/{businessId}`                   | جزئیات مجاز بررسی و پیش‌نمایش                 |
| `POST /review/businesses/{businessId}/decisions`        | تأیید، رد یا تعلیق                            |

قرارداد تصمیم شامل action، شناسه درخواست مرتبط، revision بررسی‌شده و دلیل در موارد لازم باشد. دلیل رد/تعلیق plain text، محدود و الزامی باشد.

قرارداد دقیق DTO، status، ETag و نمونه درخواست/پاسخ را پیش از اتصال UI در اسناد و OpenAPI ثبت کن.

- writeهای جدید: `Idempotency-Key`.
- تغییرات publication: `If-Match` مربوط به منبع انتشار.
- ناشناس در مسیر خصوصی: `401`.
- نقش reviewer نامعتبر: `403`.
- منبع خارج مالکیت یا سالن غیرعمومی در API عمومی: `404` یکسان.
- ورودی نامعتبر/فیلد ناشناخته: `422`.
- تعارض نسخه/وضعیت: `409`.
- نبود پیش‌شرط نسخه: `428`.
- محدودیت نرخ و خرابی وابستگی طبق قرارداد موجود.

Origin، JSON، محدودیت بدنه، خطای امن، no-store و rate limit مسیرهای نوشتنی حفظ و برای مسیرهای جدید اعمال شوند.

allowlist کلاینت و runtime decoderها را توسعه بده؛ محدودیت مسیر را برای آسان‌شدن پیاده‌سازی حذف نکن.

## ۱۰. API عمومی و جست‌وجوی فارسی

### مرز داده عمومی

DTO عمومی allowlist صریح داشته باشد و شامل این داده‌ها باشد:

- شناسه، نام، نوع و معرفی کوتاه سالن.
- شهر، محله، نشانی و موبایل عمومی.
- خدمات فعال و معتبر با دسته، قیمت صحیح IRR و مدت.
- متخصصان فعال و انتخاب‌شده برای نمایش عمومی و خدمات مجازشان.
- برنامه کاری سالن و استثناهای مرتبط در بازه محدود.
- timezone لازم برای تفسیر برنامه.

این موارد عمومی نشوند:

ایمیل مالک، credential، نشست، عضویت، مشخصات داخلی reviewer، دلایل بررسی، audit، کلیدهای idempotency، متخصص مخفی و داده‌های خصوصی.

فهرست، جزئیات، فیلتر موقعیت و هر شمارنده، فقط از سالن‌های واجد وضعیت عمومی داده بگیرند. draft، pending و suspended حتی با حدس ID عمومی نشوند.

### خواندن سازگار

خواندن چندمرحله‌ای عمومی نباید ابتدا state منتشرشده و سپس محتوای ویرایش‌شده و بررسی‌نشده را ترکیب کند.

از query واحد یا transaction خواندنی با snapshot سازگار استفاده کن. درخواست‌های جدید پس از commit لغو انتشار/تعلیق باید سالن را مخفی ببینند.

در این اسپرینت cache عمومی پایدار اضافه نکن:

- پاسخ API عمومی `no-store`.
- داده public در Next بدون cache ماندگار و بدون SSG سالن‌ها.
- پارامتر عمومی مانند `includeDraft=true` وجود نداشته باشد.
- پیش‌نمایش مالک/reviewer از مسیر احرازشده جدا بیاید.

### فیلترها

پارامترهای عمومی:

`q`، `audience`، `category`، `city`، `district`، `cursor` و `limit`.

- جست‌وجو روی نام سالن و نام خدمات عمومی معتبر.
- audience فقط زنانه/مردانه؛ نبود آن یعنی همه.
- district وابسته به city.
- limit پیش‌فرض۲۰ و حداکثر۵۰.
- q حداکثر۱۰۰، city حداکثر۸۰ و district حداکثر۱۲۰ نویسه.
- نوع نامعتبر، پارامتر تکراری مبهم و فیلد ناشناخته رد شوند.
- SQL کاملاً parameterized و wildcardهای ورودی کنترل شوند.

نرمال‌سازی مشترک و قابل تست:

- یکسان‌سازی «ی/ي» و «ک/ك».
- مدیریت اعراب و کشیدگی.
- رفتار مشخص نیم‌فاصله و فاصله‌های متوالی.
- trim و Unicode normalization مناسب.
- نرمال‌سازی یکسان ورودی و داده ذخیره‌شده.

نمایش فارسی مالک با کلید جست‌وجوی نرمال‌شده اشتباه نشود. شهرهای fixture به مرجع جغرافیایی واقعی تبدیل نشوند. اگر داده‌ای نیست، موقعیت «همه شهرها» یا حالت خالی معتبر نمایش داده شود.

pagination کلیدی با ترتیب پایدار و tie-breaker شناسه باشد. cursor به فیلتر و ترتیب وابسته و معتبرسازی شود. دقت timestamp دیتابیس هنگام cursor از بین نرود. join خدمات، سالن را چند بار در یک صفحه تکرار نکند.

قیمت «از» کمترین قیمت خدمات عمومی منطبق با فیلتر دسته باشد. محاسبه در سرور، تبدیل دقیق تومان در UI و صفر واقعی از داده ساختگی تفکیک شود.

## ۱۱. رابط کاربری

Design System فعلی، ریدیزاین اخیر، Vazirmatn، tokenهای petrol و اجزای موجود حفظ شوند.

### مدیریت مالک

مسیرهای پیشنهادی:

- `/manage/[businessId]/publication`

نمایش بده:

- وضعیت انتشار با متن و رنگ مناسب.

- پیش‌نمایش.

- `demoSalons` از importهای runtime حذف شود.
- فیلتر و pagination از API واقعی بیایند.
- فیلترهای غیرخصوصی در URL قابل اشتراک باشند.

- loading، empty، error و retry کامل باشند.
- خطا با «هیچ سالنی وجود ندارد» اشتباه نشود.
- کارت، لینک واقعی پروفایل باشد و بازکردن در تب جدید کار کند.

### پروفایل عمومی

مسیر پایدار `/salons/[businessId]` باشد؛ UUID سالن در کد هاردکد نشود.

نمایش:

- خدمات و قیمت/مدت واقعی.
- متخصصان عمومی.
- موقعیت و اطلاعات تماس عمومی.
- ساعات کاری و روزهای خاص؛ با توضیح روشن اینکه ساعات، وقت آزاد رزرو نیستند.

برای سالن غیرعمومی، صفحه مستقیم رفتار 404 واقعی داشته باشد. metadata و داده صفحه نیز اطلاعات خصوصی را افشا نکنند. مستندات نصب‌شده Next برای route، params، fetching و notFound خوانده شوند.

دکمه «رزرو» اضافه نکن. برای موبایل عمومی معتبر، لینک تماس قابل استفاده و اطلاعات واقعی باشد؛ امتیاز، نظر، فاصله و تصویر سالن نمونه نساز.

### معیار موبایل

## ۱۲. migration و حذف نمونه

migration بعدی را با شماره آزاد واقعی بساز؛ SQL و snapshotهای اجراشده0000..0003 را بازنویسی نکن.

تغییرهای لازم شامل این موارد است:

- مرجع دسته‌ها و ارتباط خدمات.
- معرفی کوتاه سالن و انتخاب نمایش عمومی متخصص.
- توسعه قید state سالن.
- revision و metadata انتشار.
- درخواست‌ها/تصمیم‌ها و سابقه لازم.
- دسترسی reviewer و ثبت تغییر آن.
- index و FKهای واقعی موردنیاز queryها.

طرح نهایی ستون‌ها و جدول‌ها را در ADR و data-model ثبت کن. دو منبع ناسازگار برای state سالن نساز.

قواعد ارتقا:

- حساب، رمز، نشست، سالن، خدمات، تخصیص‌ها و ساعات موجود حفظ شوند.
- سالن قدیمی خودکار منتشر نشود.
- متخصص قدیمی خودکار عمومی نشود.
- category نامشخص با داده حدسی پر نشود.
- قیدهای tenant، exclusion، trigger و audit قبلی حفظ شوند.
- fixtureهای تست و مدارک تاریخی حفظ، اما از runtime جدا شوند.
- عکس و نام سالن نمونه به سالن واقعی نسبت داده نشوند.
- دیتابیس توسعه reset یا با نمونه‌ها پر نشود.

indexها بر query واقعی متکی باشند. N+1، query بی‌کران و countهای غیرضروری بررسی شوند. Redis، Elasticsearch یا موتور جست‌وجوی تازه اضافه نکن. با dataset کنترل‌شده، queryهای اصلی و EXPLAIN مناسب را ثبت کن؛ مقیاس‌پذیری نامحدود ادعا نکن.

## ۱۳. تست‌های ضروری

### Unit

- انتقال وضعیت‌های مجاز و نامجاز.
- آمادگی و نقص‌های دقیق.
- نرمال‌سازی فارسی.
- اعتبار فیلتر و cursor.
- تبدیل پول.
- قواعد نمایش عمومی و نسخه‌های مرتبط.

### HTTP و قرارداد

- boot واقعی Nest و DI.
- DTO/OpenAPI مسیرهای جدید.
- auth، role، Origin، input و خطای امن.
- نبود شرط تأیید ایمیل و نبود بازگشت MFA.
- فیلد ناشناخته و mass assignment.
- مخفی‌بودن داده خصوصی در پاسخ عمومی.

### PostgreSQL واقعی

- fresh migration و upgrade داده‌دار اسپرینت۴.
- rerun بدون اثر اضافه.
- owner و reviewer مجاز/غیرمجاز و منع self-review.
- تأیید نسخه کهنه.
- approval هم‌زمان با تغییر خدمت، متخصص، ساعات و مشخصات.
- approve/reject هم‌زمان.
- تعلیق هم‌زمان با درخواست خواندن عمومی.
- ابطال درخواست pending پس از ویرایش.
- عدم نشت محتوای بررسی‌نشده در خواندن چندquery.
- replay، payload متفاوت، rollback و audit دقیقاً یک‌بار.
- لغو دسترسی قبل از replay.
- عدم تکرار سالن در pagination و cursor وابسته به فیلتر.
- دیتابیس خالی بدون fallback نمونه.
- صفر، سقف و تبدیل صحیح قیمت.

### مرورگر واقعی

با Next، Nest و PG واقعی و DB موقت:

1. مالک وارد شود؛ ایمیل تأییدنشده مانع نباشد.
2. سالن و داده لازم را تکمیل کند.
3. نقص‌ها را ببیند و اصلاح کند.
4. پیش‌نمایش خصوصی و رضایت را ثبت کند.
5. reviewer مستقل درخواست را بررسی و تأیید کند.
6. ناشناس سالن را در کشف و لینک مستقیم ببیند.
7. ویرایش مالک، سالن را خصوصی و نیازمند درخواست تازه کند.
8. رد با دلیل، اصلاح و درخواست مجدد.
9. تعلیق و حذف از کشف/لینک عمومی.
10. فیلتر فارسی، URL، back/forward، قطع شبکه و پاسخ دیررس.
11. URL سالن دیگران، خروج و لغو دسترسی reviewer.
12. موبایل، صفحه‌کلید و متن۲۰۰٪.

مسیر موفق اصلی با mock شبکه جایگزین نشود. داده کنترل‌شده فقط در DB موقت باشد.

scriptهای واقعی را از package.json بخوان. نصب frozen و `pnpm run check` نسخه نهایی اجرا شوند. تست یا assertion قبلی برای سبزشدن حذف یا ضعیف نشود.

build و migration را هم‌زمان روی یک dist مشترک اجرا نکن. فرایندها و DBهای تست مالکیت مشخص و teardown قابل اثبات داشته باشند. خرابی محیط، تست اجرا‌نشده و تکرار موفق را جدا گزارش کن.

CI remote تا قبل از push مجاز کارفرما اجراشده فرض نشود.
