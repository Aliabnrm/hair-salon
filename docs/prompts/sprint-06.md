### معنای دقیق «زمان قابل ارائه»

baseline اسپرینت۵ هنوز Appointment یا دفتر اشغال ندارد. این اسپرینت از برنامه واقعی سالن/متخصص و استثناها، ظرفیت قابل ارائه طبق برنامه را محاسبه می‌کند. هیچ رزرو واقعی را فرض یا تولید نکن.

- پاسخ API صریحاً `availability_basis: "schedule_only"` و `booking_enabled: false` داشته باشد.
- UI با متن ساده بگوید: «زمان‌ها بر اساس برنامه ثبت‌شده سالن هستند؛ ثبت آنلاین نوبت هنوز فعال نیست.»
- انتخاب ساعت فقط انتخاب UI است؛ پیام موفقیت رزرو، کد پیگیری، نگه‌داشتن ظرفیت و دکمه تأیید رزرو وجود نداشته باشد.
- موتور خالص قابلیت کسر بازه اشغال ورودی را داشته باشد تا در اسپرینت۷ همان قانون استفاده شود؛ آزمون با بازه اشغال مصنوعی فقط در تست مجاز است.
- در runtime این baseline، نبود مدل رزرو را در mapping صریح و مستند نشان بده. خرابی DB یا شکست خواندن را به busy=[]، موفقیت یا فهرست خالی تبدیل نکن.
- برای آینده، جدول خالی رزرو/مسدودی، FakeRepository، adapter همیشه‌موفق یا سرویس نمایشی نساز. اتصال اشغال واقعی و ثبت اتمیک متعلق به اسپرینت۷ است؛ تقویم تلفنی/حضوری پیش‌شرط پایلوت واقعی خواهد بود.
- اگر در زمان اجرا، baseline معتبر واقعاً مدل اشغال مصوب تازه‌ای داشت، آن را بخوان و طرح/قرارداد را با شاهد هماهنگ کن؛ مدل موجود را نادیده نگیر و سیستم دوم نساز.

## ۳. معماری و ساختار هدف

NestJS feature-first Modular Monolith، Next.js App Router/React، PostgreSQL/Drizzle و یک pnpm workspace حفظ شوند. فعلاً availability خواندنی در bounded context موجود سالن قرار بگیرد؛ ماژول رزرو کامل، CQRS، microservice یا DB دوم نساز.

ساختار هدف، با امکان تطبیق نام محدود بر اساس کد واقعی:

```text
backend/src/modules/salon-management/
  domain/availability/
    availability.types.ts          # ورودی/خروجی خالص و سیاست
    availability-policy.ts         # محاسبه، بافر، اشغال و ادغام نتیجه
    time-range.ts                  # فقط عملیات زمانی واقعاً لازم
    *.spec.ts
  application/availability/
    availability.service.ts        # orchestration خواندن و محاسبه
  application/ports/
    availability-reader.ts         # snapshot محدود و همساز از داده واقعی
    clock.ts                       # زمان سرور قابل کنترل در تست، در صورت نیاز واقعی
  infrastructure/persistence/
    postgres-availability-reader.ts
  infrastructure/time/             # پیاده‌سازی ساعت/تبدیل timezone در صورت نیاز
  presentation/http/
    availability.controller.ts
    dto/availability.dto.ts
frontend/src/features/availability/
  api/                             # transport و runtime decoding
  model/                           # type، URL و تبدیل خالص موردنیاز
  hooks/                           # انتخاب‌ها، دریافت و پاسخ دیررس
  components/                      # انتخاب خدمت/متخصص/روز/وقت و خلاصه
  index.ts
frontend/src/app/salons/[businessId]/times/
  page.tsx                         # ترکیب route و boundary داده
```

- Controller فقط HTTP، validation مرزی و Application را بداند؛ query و قانون زمان در آن نباشد.
- Application خواندن، زمان سرور و domain را هماهنگ کند؛ جزئیات SQL در Reader باشد.
- domain به Nest، pg/Drizzle، React و request وابسته نباشد. now ورودی صریح محاسبه باشد؛ Date.now در حلقه slot یا تست پراکنده نشود.
- Port فقط برای مرز واقعی خواندن/زمان؛ GenericRepository و wrapperهای بی‌مسئولیت نساز.
- عملیات بازه موجود مانند intersectIntervals، minute و clock را بررسی و در صورت سازگاری reuse کن. قانون یکسان را در UI/SQL دوباره پیاده نکن. استخراج مشترک فقط برای استفاده واقعی و با تست رفتار قبلی باشد.
- componentها کوچک و مسئولیت‌دار؛ component نزدیک۲۰۰خط یا با شرط‌های ترکیبی زیاد بازبینی شود. شکستن مکانیکی بر اساس تعداد خط کافی نیست.
- hook برای هماهنگی stateful؛ محاسبه تاریخ، بازه و تبدیل مبلغ تابع معمولی باشد.
- profile عمومی/خصوصی مشترک را به محل منطق availability تبدیل نکن؛ ورود به مسیر times در ترکیب صفحه عمومی انجام شود. پیش‌نمایش مالک/reviewer، دعوت عمومی نامعتبر نگیرد.
- strict TypeScript، constructor DI، import type درست؛ any، ts-ignore و cast برای پنهان‌کردن خطا ممنوع.

## ۴. قواعد دقیق موتور زمان

### ساعت، تاریخ و محدوده

- منبع now، ساعت سرور با یک snapshot زمانی برای هر درخواست است؛ ساعت دستگاه مشتری مجوز زمان نمی‌سازد.
- timezone کسب‌وکار فعلی `Asia/Tehran` است؛ offset ثابت +03:30 در محاسبه هاردکد نشود.
- تاریخ API، روز محلی ISO میلادی است؛ نمایش UI شمسی و ساعت۲۴ساعته باشد. از جابه‌جایی روز بر اثر UTC یا timezone مرورگر جلوگیری کن.
- گام۱۵دقیقه روی نیمه‌شب محلی تراز شود: ۰۰:۰۰،۰۰:۱۵ و…؛ اگر شیفت۰۹:۱۰ شروع شود، گام با۰۹:۱۰ تراز نمی‌شود.
- شروع خدمت باید `starts_at >= now + 60 minutes` باشد؛ مرز دقیق مجاز است.
- افق۳۰روز شامل امروز تهران تا پایان روز today+29 است. ساعت بعد از نیمه‌شب، روز مجاز و حداقل فاصله دوباره از سرور تعیین شوند.
- از مهلت now تا۳۰×۲۴ساعت به‌جای روزهای محلی استفاده نکن.
- محاسبه درخواست حداکثر هفت روز شامل دو سر بازه باشد؛ from<=to و همه روزها داخل افق جاری.
- روز گذشته یا خارج افق، تاریخ نامعتبر، بازه بیش ازهفت روز و timezone ورودی دلخواه رد شوند.
- شروع `24:00` نامعتبر؛ پایان `24:00` فقط مرز پایان روز است. خدمت/اشغال از روز محلی عبور نکند؛ پایان دقیق در مرز نیمه‌شب، انتهای همان روز محسوب شود و در UTC instant درست داشته باشد.
- تبدیل timezone رفتار مشخص برای زمان تاریخی ناموجود/مبهم داشته باشد. زمان ناموجود slot نسازد؛ در زمان مبهم instantهای دارای offset متفاوت با هم یکی نشوند. تست تاریخی با clock کنترل‌شده باشد، نه درخواست عمومی خارج افق.
- ابتدا امکانات استاندارد/موجود را بررسی کن. تنها اگر تبدیل معتبر timezone به dependency واقعی نیاز داشت، یک کتابخانه نگهداری‌شده با دلیل، مستند رسمی، سازگاری نسخه و lockfile انتخاب کن؛ چند کتابخانه هم‌پوشان یا پیاده‌سازی دست‌ساز پیچیده DST نساز.

### برنامه مؤثر هر روز

1. برنامه هفتگی سالن را با exception فعال همان روز و همان scope تعیین کن؛ exception جایگزین برنامه روز می‌شود، نه اینکه با آن جمع شود.
2. exception با closed=true، برنامه آن scope را خالی می‌کند؛ با closed=false، intervalهای exception جایگزین‌اند.
3. برای هر متخصص همین قاعده مستقل اعمال شود؛ deleted_at و scope سالن دیگر نادیده گرفته شوند.
4. اشتراک برنامه مؤثر سالن و متخصص، مبنای ارائه خدمت است. تعطیلی سالن با بازبودن استثنایی متخصص دور زده نشود.
5. نبود برنامه و نبود exception بازکننده، به معنی بسته‌بودن است. فاصله بین intervalها استراحت است.
6. بازه‌ها مرتب و بدون تکرار شوند؛ بازه‌های واقعاً مجاور در یک برنامه پیوسته قابل ادغام‌اند. فاصله واقعی بین دو بازه هرگز با جمع مدت پنهان نشود.

### مدت، بافر و اشغال

برای شروع خدمت s:

```text
serviceEnd = s + duration
occupiedStart = s - bufferBefore
occupiedEnd = serviceEnd + bufferAfter
```

تمام `[occupiedStart, occupiedEnd)` باید داخل یک بازه پیوسته مجاز همان روز جا شود. duration و بافر واقعی از service سمت سرور خوانده شوند؛ مدت لازم نیست مضرب۱۵ باشد. بافرها در طول خدمت نمایشی ادغام نشوند؛ UI مدت خدمت و شروع/پایان آن را درست نشان دهد.

- بازه نیمه‌باز است؛ `[a,b)` با `[b,c)` تداخل ندارد.
- هر busy interval ورودی، اشغال کامل شامل بافرهای خودش است؛ دو بار بافر روی آن اعمال نکن.
- busyهای هم‌پوشان/مجاور ابتدا نرمال شوند؛ full containment، پوشاندن کامل روز و عبور busy از مرز بازه query درست مدیریت شوند.
- ظرفیت منفی، slot تکراری، interval صفر/منفی و عبور از استراحت تولید نشود.
- eligibility فقط از خدمت فعال/دسته معتبر، متخصص فعال و عمومی، تخصیص همان سالن و برنامه مجاز بیاید. متخصص خصوصی حتی در انتخاب «اولین آزاد» حضور نداشته باشد.
- سالن غیرpublished هیچ ظرفیت عمومی نداشته باشد.

### انتخاب متخصص

- متخصص مشخص: فقط همان متخصص واجد شرایط.
- `any`: اجتماع زمان‌های متخصصان واجد شرایط؛ یک شروع/پایان یکسان فقط یک بار نمایش داده شود.
- تعداد متخصصان واجد برای هر slot از واقعیت محاسبه شود؛ تعیین یا وعده متخصص نهایی در این اسپرینت انجام نشود.
- ترتیب خروجی با instant شروع و tie-breaker مشخص پایدار باشد؛ ترتیب دریافت سطر DB نتیجه را عوض نکند.

نمونه تست: برنامه مشترک۱۰:۰۰–۱۲:۰۰، خدمت۳۰دقیقه، بافر قبل۱۰ و بعد۵، بدون busy و با now مجاز؛ شروع‌ها روی گام۱۵دقیقه از۱۰:۱۵ تا۱۱:۱۵ هستند. مجموع۴۵دقیقه اشغال است و شروع۱۱:۳۰ بیرون می‌افتد. نمونه جدا: دو بازه۲۰دقیقه‌ای با فاصله، خدمت۳۰دقیقه‌ای را جا نمی‌دهند.

## ۵. خواندن واقعی، سازگاری و حریم خصوصی

Reader، انتشار، خدمت/بافر، متخصص/تخصیص، ساعات و استثناهای محدوده را از یک snapshot سازگار بخواند: یک statement یا transaction خواندنی REPEATABLE READ با cleanup درست. ابتدا published خواندن و سپس برنامه بررسی‌نشده از snapshot دیگر ممنوع است.

- داده برنامه/بافر از schema واقعی خوانده شود؛ API عمومی فعلی بافر ندارد و نباید داده حدسی جایگزین آن شود.
- tenant همه JOINها و FKهای مرتبط صریح باشد.
- request تازه پس از commit توقف انتشار/ویرایش/تعلیق،404 بگیرد. درخواست در حال اجرا می‌تواند snapshot پیش از commit را ببیند؛ تضمین push فوری اختراع نکن.
- write مسیر مدیریت، revision، idempotency و سیاست انتشار۵ را تغییر نده مگر رفع باگ لازم و مستند با تست سازگاری.
- خواندن بدون write محصول و بدون ایجاد audit/رزرو/تغییر content_revision باشد؛ سهمیه امنیتی فعلی می‌تواند metadata موقت خود را ثبت کند.
- سقف‌ها را از پروژه واقعی بگیر: حداکثر۱۰۰خدمت و۵۰متخصص هر سالن،۲۸بازه هفتگی هر scope و چهار بازه در روز. خواندن استثناها فقط همان بازه query باشد.
- query جدا برای هر متخصص/هر روز نساز؛ خواندن گروهی با تعداد query ثابت و محدود انجام شود.
- فقط DTO allowlist برگردان: زمان‌ها، شمارش متخصصان عمومی واجد، خدمت عمومی، محدوده و سیاست لازم.
- ایمیل/عضویت/نشست، دلیل تعطیلی یا بررسی، audit، متخصص مخفی و identity افراد عمومی نشوند. busyهای تست یا آینده با شناسه مشتری/رزرو در پاسخ نیایند.
- هیچ cache عمومی پایدار، SSG زمان‌ها، fallback نمونه، Redis یا موتور جست‌وجوی تازه اضافه نکن. GETها و fetch Next/مرورگر no-store باشند.

## ۶. قرارداد HTTP هدف

مسیر عمومی جدید زیر پیشوند موجود:

```text
GET /api/v1/catalog/salons/{businessId}/availability
```

| ورودی      | قرارداد                                                           |
| ---------- | ----------------------------------------------------------------- |
| businessId | UUID معتبر؛ سالن منتشرشده                                         |
| service_id | UUID الزامی؛ خدمت فعال و عمومی معتبر همان سالن                    |
| staff_id   | اختیاری؛ `any` پیش‌فرض یا UUID متخصص عمومی واجد همان خدمت         |
| from / to  | هر دو غایب یا هر دو حاضر؛ روز محلی ISO و inclusive، حداکثرهفت روز |

در نبود from/to، سرور امروز تهران تا min(today+6,lastAllowedDate) را محاسبه کند. بدین ترتیب bootstrap به ساعت مرورگر وابسته نیست. هیچ duration،price،buffer،state،includeDraft یا timezone قابل تزریق از کلاینت پذیرفته نشود. query تکراری مبهم، آرایه و فیلد ناشناخته422 باشند.

نمونه شکل data در envelope جاری؛ نام نهایی فیلدها در DTO/OpenAPI و مستند قرارداد هماهنگ شوند:

```json
{
  "business_id": "<uuid>",
  "service": { "id": "<uuid>", "name": "کوتاهی مو", "price_irr": 2500000, "duration_minutes": 30 },
  "staff_id": "any",
  "timezone": "Asia/Tehran",
  "checked_at": "<UTC instant>",
  "availability_basis": "schedule_only",
  "booking_enabled": false,
  "policy": {
    "slot_step_minutes": 15,
    "minimum_notice_minutes": 60,
    "first_allowed_date": "<local ISO date>",
    "last_allowed_date": "<local ISO date>"
  },
  "from": "<local ISO date>",
  "to": "<local ISO date>",
  "days": [
    {
      "local_date": "<local ISO date>",
      "slots": [
        { "starts_at": "<UTC instant>", "ends_at": "<UTC instant>", "start_local": "10:15", "end_local": "10:45", "available_staff_count": 2 }
      ]
    }
  ]
}
```

- همه روزهای بازه، حتی بدون slot، به ترتیب حضور داشته باشند؛ slots=[] موفقیت معتبر است.
- شمارش staff فقط متخصص واجد فعال/عمومی را دربرگیرد؛ در حالت متخصص مشخص برای slot معتبر برابر۱ است. آرایه شناسه۵۰متخصص برای هر slot لازم نیست.
- کران خروجی با بازه هفت‌روزه، گام۱۵ و گروه‌بندی enforce شود؛ سقف دفاعی۷۰۰slot برای هر پاسخ، بدون truncation خاموش. رسیدن غیرمنتظره به سقف، خطای امن و قابل مشاهده بدهد؛ روزهای حذف‌شده را بسته نمایش نده.
- سالن غیرعمومی، خدمت متعلق به دیگری/غیرفعال و متخصص خصوصی/نامعتبر همان404 عمومی داشته باشند؛ UUID با قالب غلط422 است.
- خطای زیرساخت503 طبق قرارداد فعلی، rate limit برابر429 همراه Retry-After؛ هیچ خطای خام DB/stack نمایش داده نشود.
- share سقف عمومی catalog فعلی حفظ و برای محاسبه availability سقف اختصاصی۶۰درخواست/IP/دقیقه با limiter موجود اعمال شود؛ bypass با ورود یا پارامتر دلخواه ایجاد نشود. proxy واقعی و سهمیه مشترک NAT مستند بمانند.
- OpenAPI شامل queryها، schema دقیق، مثال معتبر، statusها، no-store و مرز schedule_only باشد. کلاینت allowlist و runtime decoder توسعه یابند؛ allowlist حذف نشود.
- این GET ظرفیت رزرو نمی‌کند؛ If-Match/Idempotency-Key، quote پایدار یا token تضمین وقت برای آن اختراع نکن.

## ۷. تجربه کاربری موبایل و URL

مسیر پیشنهادی `/salons/[businessId]/times` و لینک «بررسی زمان‌ها» از صفحه عمومی سالن باشد. UUID سالن/متخصص/خدمت هاردکد نشود؛ هیچ ورود اجباری برای مشاهده زمان‌ها ایجاد نشود.

اجزای تجربه:

1. هویت کوتاه سالن و بازگشت روشن به صفحه آن.
2. انتخاب یک خدمت با نام/قیمت/مدت واقعی.
3. متخصص مشخص یا «اولین متخصص آزاد»؛ توضیح کوتاه که نام نهایی هنگام ثبت آینده تعیین می‌شود.
4. انتخاب روز شمسی در افق مجاز با شروع هفته شنبه؛ عنوان ماه/سال، امروز و روز منتخب واضح باشند.
5. نمایش گروه زمان‌ها با ساعت۲۴ساعته و هدف لمس مناسب؛ روز بدون وقت، loading و خرابی شبکه ظاهر متفاوت داشته باشند.
6. خلاصه انتخاب: خدمت، متخصص یا any، روز، شروع/پایان و قیمت تومان؛ متن روشن نبود امکان ثبت آنلاین. دکمه بی‌عمل «ادامه/تأیید رزرو» نساز.
7. تغییر انتخاب و دکمه دریافت دوباره زمان‌ها؛ هنگام پاسخ خطا، intent معتبر حفظ شود و موفقیت نمایشی ساخته نشود.

`service_id`،`staff_id` و `date` در URL قابل اشتراک باشند؛ در صورت نگهداری شروع منتخب در URL، قالب UTC آن validate و پس از دریافت تازه با slotهای واقعی تطبیق داده شود. هیچ داده خصوصی یا auth در URL نباشد.

- URL ورودی validate شود؛ داده نامعتبر با انتخاب تصادفی/آرام جایگزین نشود. راه اصلاح روشن داشته باشد.
- از response اولیه بدون from/to، تاریخ سرور و حدود تقویم را بگیر. لینک تاریخ منقضی، خطای قابل فهم و اقدام «بازگشت به تاریخ‌های مجاز» داشته باشد.
- تغییر خدمت، متخصص نامعتبر قبلی و ساعت منتخب را پاک کند؛ تاریخ در صورت معتبرماندن حفظ شود.
- تغییر متخصص/روز، ساعت قبلی را پاک کند. ساعت منتخب فقط وقتی پس از دریافت تازه هنوز موجود است قابل نمایش به‌عنوان انتخاب باشد.
- back/forward و reload، انتخاب‌های معتبر URL را بازیابی کنند. درخواست قبلی abort و پاسخ دیررس با sequence/key نادیده گرفته شود.
- هنگام refresh یا خطا، slot پاسخ قبلی به‌عنوان داده تازه قابل انتخاب نباشد. refetch هنگام بازگشت focus و اقدام دستی کافی است؛ polling ثانیه‌ای، شمارش معکوس نگه‌داشتن وقت یا ادعای realtime نساز.
- پس از404/توقف انتشار، فهرست زمان قدیمی پنهان و راه بازگشت به کاوش نشان داده شود.
- مبلغ با تابع موجود و دقیق IRR→تومان؛ صفر واقعی حفظ شود. محاسبه ظرفیت در فرانت تکرار نشود.

Design System، Vazirmatn، tokenهای petrol و AppShell فعلی حفظ شوند. component/primitive مشترک فقط بعد نیاز واقعی استخراج شود. صفحه تقویم غول‌آسا و کتابخانه date picker بدون بررسی گزینه موجود نساز.

عرض‌های۳۲۰/۳۶۰/۳۹۰/۴۳۰ و۷۶۸/۱۴۴۰، متن۲۰۰٪، نام بلند، RTL/LTR موضعی، صفحه‌کلید، focus-visible، label/aria، reduced-motion و عدم پوشانده‌شدن عملیات توسط نوار پایین بررسی شوند. کنترل لمسی حداقل۴۴پیکسل و ورودی خوانا باشد. اگر role=grid استفاده شد، رفتار صفحه‌کلید متناظر کامل باشد؛ role نمایشی بدون رفتار اضافه نکن. audit کامل دسترس‌پذیری بدون شاهد ادعا نشود.

## ۸. دیتابیس، dependency و عملکرد

این برش خواندنی است؛ migration جدید پیش‌فرض ندارد. 0000..0004، snapshotهای اجراشده، داده توسعه و قواعد انتشار حفظ شوند. مدت/بافر/ساعات از ستون‌های واقعی فعلی خوانده شوند؛ ستون فرضی برای آینده اضافه نکن.

اگر EXPLAIN و query واقعی نیاز به index تازه را نشان داد، تغییر حداقلی با شماره migration آزاد واقعی، SQL/snapshot معتبر، حفظ قیود قبلی و تست fresh/upgrade/rerun انجام شود. دلیل و نتیجه واقعی در ADR/گزارش بیاید؛ صرف ساخت index شاهد بهبود نیست. مدل Appointment/ScheduleAllocation برای پرکردن دامنه این اسپرینت اضافه نشود.

- dataset موقت شامل چند متخصص، خدمت، برنامه و exception واقعی باشد؛ N+1، تعدادquery، حجم پاسخ و هزینه محاسبه در حالت any سنجیده شوند.
- EXPLAIN ANALYZE/BUFFERS queryهای اصلی Reader با همان query واقعی ثبت شود؛ dataset کوچک را benchmark مقیاس واقعی معرفی نکن.
- نسخه‌ها را بی‌دلیل ارتقا نده؛ فقط pnpm و lockfile ریشه. نیاز واقعی timezone در صورت افزودن dependency، دلیل و مرجع رسمی و سازگاری Node/TS ثبت شود.
- env و secret پراکنده نشوند؛ telemetry، سرویس خارجی و نصب global اضافه نشود.

## ۹. تست‌های لازم

### Unit دامنه و تبدیل

- ساعت/تاریخ کنترل‌شده؛ مرز دقیق۶۰دقیقه و افق۳۰روز تقویمی.
- امروز نزدیک نیمه‌شب، هفته شنبه، تغییر ماه و اسفند/کبیسه در تبدیل نمایشی.
- اشتراک ساعات، برنامه خالی، exception جایگزین/بسته/حذف‌شده و اولویت تعطیلی سالن.
- مدت نامضرب۱۵، بافر قبل/بعد/صفر، پایان دقیق بازه و۲۴:۰۰، منع عبور خدمت/اشغال از روز.
- استراحت واقعی، بازه مجاور، هم‌پوشانی busy، containment و تماس مرزی نیمه‌باز.
- کسر busy ورودی فقط در تست موتور؛ عدم دوباره‌شماری بافر busy.
- any با دو متخصص، حذف تکرار و count درست؛ مستقل‌بودن نتیجه از ترتیب input.
- تبدیل timezone و gap/fold تاریخی با clock مناسب؛ ساعت نامعتبر slot نسازد.
- کران داده، خطای ورودی و تبدیل دقیق پول با helper موجود.

### HTTP و PostgreSQL واقعی

- boot واقعی Nest/DI، OpenAPI، DTO و envelope؛ API عمومی بدون session.
- unknown/duplicate query، UUID/تاریخ غلط، from/to ناقص، بازه بیش‌از۷روز، گذشته/افق و input تزریقی.
- draft/pending/suspended404؛ خدمات و متخصص سالن دیگر404؛ متخصص مخفی و تخصیص نامعتبر وارد any نشوند.
- دامنه service و buffer از DB واقعی؛ closed/override و روزهای خالی با fixture کنترل‌شده.
- نبود نشت اطلاعات خصوصی در کل response و خطا، no-store و429/Retry-After.
- DB unavailable به503، نه slots=[] یا fallback نمونه.
- خواندن سازگار هنگام ویرایش برنامه/خدمت یا تعلیق: snapshot قدیمی منسجم یا404؛ محتوای ترکیبی ممنوع. request بعد commit404 باشد.
- GET روی جدول‌های محصول هیچ Appointment/اثر مدیریت/revision تازه نسازد؛ سهمیه موقت امنیتی جدا بررسی شود.
- fresh و rerun schema جاری؛ اگر migration تازه لازم شد، upgrade داده‌دار و حفظ قیود/داده نیز تست شوند.

### مرورگر واقعی با Next/Nest/PG و DB موقت

1. سالن کنترل‌شده دارای service/staff/hours و publication معتبر؛ fixture فقط در DB متعلق به تست.
2. ناشناس از صفحه عمومی به times برود و خدمت/متخصص/روز را انتخاب کند؛ ساعت‌ها با داده واقعی مطابقت داشته باشند.
3. لینک مستقیم، reload، back/forward و انتخاب any/متخصص مشخص.
4. انتخاب ساعت و خلاصه؛ تغییر خدمت/متخصص/روز انتخاب ساعت قبلی را پاک کند.
5. روز تعطیل و بدون وقت، شبکه قطع و retry، درخواست دیررس و انتخاب سریع چند روز.
6. قیمت/مدت و داده جدید بعد refresh؛ سالن غیرعمومی/متخصص مخفی و URL دستکاری‌شده.
7. مرز امروز/افق با ساعت قابل کنترل در fixture؛ clock یا route آزمایشی در production اضافه نشود.
8. عرض‌های موبایل/دسکتاپ، keyboard/focus، متن۲۰۰٪ و عدم تداخل با AppShell.
9. پیام schedule_only و نبود ادعای ثبت موفق/نگه‌داشتن ظرفیت/کد پیگیری.

مسیر موفق با mock شبکه جایگزین نشود. intercept فقط برای سناریوی شبکه/تأخیر باشد. assert یا تست قبلی برای سبزشدن حذف/ضعیف نشود؛ شمارش تست هدف کیفیت نیست.

فرمان‌ها را از package.json واقعی بخوان؛ frozen install و `pnpm run check` نهایی با PostgreSQL و مرورگر واقعی اجرا شوند. Chrome fallback فقط در صورت نیاز محیط و طبق روش موجود مستند شود. نتیجه قبلی۲۶۱تست اسپرینت۵، شاهد نسخه۶ نیست. build/migrate هم‌زمان روی dist مشترک اجرا نشوند؛ DB/process و کپی موقت frontend مالکیت و teardown روشن داشته باشند. تصاویر جدید، شواهد تاریخی docs را overwrite نکنند. CI remote پیش از push کارفرما اجراشده فرض نشود.

## ۱۰. ترتیب اجرا و مدارک پایان

1. baseline/Git و تصمیم‌های مصوب را تطبیق بده؛ ADR بعدی با شماره آزاد برای semantics زمان و مرز schedule_only ثبت کن.
2. type/سیاست/قرارداد HTTP و تست مرزی را تثبیت کن.
3. موتور خالص و ساعت قابل کنترل، Reader snapshot واقعی و اتصال DI را پیاده کن.
4. API و آزمون privacy/consistency/rate را تکمیل کن.
5. صفحه انتخاب موبایل، URL state و مسیر عمومی را وصل کن.
6. تست واقعی کامل، مرور کد، عملکرد و cleanup را انجام بده.
7. اسناد و آموزش و گزارش را با نتیجه واقعی تکمیل کن؛ اسپرینت۷ شروع نشود.

اسناد نهایی مرتبط:

- طرح۶ و برنامه اسپرینت‌ها؛ همین prompt فقط برای هماهنگی با تغییر مصوب اصلاح شود.
- ADR جدید، `docs/architecture/sprint-06-structure.md`، قرارداد API، مدل دامنه/امنیت و README اجرای محلی.
- `docs/planning/sprints/sprint-06-report.md` و `docs/learning/sprint-06.md` فقط پس از اجرای واقعی ایجاد شوند.
- منابع رسمی مرتبط با نسخه نصب‌شده، خصوصاً Next برای route/params/searchParams/fetch/notFound و ابزار timezone انتخاب‌شده، واقعاً خوانده و در `docs/references/sprint-06-engineering-sources.md` با برداشت و محدودیت ثبت شوند. ادعای «بهترین GitHub در۲۰۲۶» بدون شاهد مطرح نشود.

آموزش فارسی با فایل واقعی و مثال ساده: interval نیمه‌باز، مدت در برابر اشغال و بافر، override در برابر جمع برنامه، local date در برابر UTC instant، clock قابل تست، Reader/Port در برابر domain، server/URL/UI state، پاسخ دیررس و تفاوت availability پیشنهادی با ثبت اتمیک رزرو. توضیح بده چرا هر جداسازی لازم است؛ اصطلاح بدون مثال کافی نیست.

تحویل نهایی شامل: قابلیت‌ها و دلیلشان، فایل‌های اصلی، مسیر تست دستی، نتیجه دقیق فرمان‌ها و اجرا‌نشده‌ها، baseline/migration/حفظ داده، شاهد query و محدودیت، وضعیت/diff محلی و پیام‌های پیشنهادی commit انگلیسی باشد. مرز import، تکرار، خطای بلعیده‌شده، داده حساس، DST/مرزروز، timeout و state کهنه review شوند.

**هیچ commit، push، ساخت/merge PR، deploy، اعطای دسترسی واقعی reviewer، reset/seed داده توسعه، پیام به چت دیگر یا شروع اسپرینت۷ انجام نده.** تغییرهای اجرا برای بررسی و ثبت کارفرما باقی بمانند.
